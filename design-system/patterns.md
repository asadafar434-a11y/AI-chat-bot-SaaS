# Паттерны сборки

Как из компонентов AI Elements собираются экраны. Раскладки взяты со страницы
**Demo** в Figma — там пять эталонных экранов: `chatbot`, `tool`, `artifact`, `IDE`, `canvas`.

---

## 1. Базовый чат (экран `chatbot`)

Самая частая раскладка и отправная точка для чата поддержки.

```
колонка 464–768 px
┌──────────────────────────┐
│  Conversation            │  flex-1, скролл, прилипание к низу
│  └─ ConversationContent  │  padding 16, gap между сообщениями 16
│       Message (user)     │
│       Message (assistant)│
│  └─ ConversationScroll…  │  всплывает, когда лента отскроллена вверх
├──────────────────────────┤
│  зона ввода   padding 16 │
│  └─ PromptInput          │
└──────────────────────────┘
```

Измерения из макета: колонка чата **464** (компактная) или **768** (просторная);
внутренние отступы `ConversationContent` — **16**; шаг между сообщениями — **16**;
зона ввода — обёртка с `padding 16` вокруг `PromptInput`.

```tsx
<div className="flex h-full flex-col">
  <Conversation className="flex-1">
    <ConversationContent>
      {messages.length === 0 && <ConversationEmptyState />}
      {messages.map((m) => (
        <Message from={m.role} key={m.id}>
          <MessageContent>
            <MessageResponse>{m.text}</MessageResponse>
          </MessageContent>
        </Message>
      ))}
    </ConversationContent>
    <ConversationScrollButton />
  </Conversation>

  <div className="p-4">
    <PromptInput onSubmit={handleSubmit}>
      <PromptInputBody><PromptInputTextarea /></PromptInputBody>
      <PromptInputFooter>
        <PromptInputTools>{/* … */}</PromptInputTools>
        <PromptInputSubmit status={status} />
      </PromptInputFooter>
    </PromptInput>
  </div>
</div>
```

## 2. Чат с инструментами (экран `tool`)

Колонка **768** по центру области 1280. Ответ ассистента — составной:
внутри одного `Message` идут `Tool`, `Reasoning`, `Sources` и текст.
Справа в подвале ввода — бейдж `Context` (78×32) с расходом токенов.

```tsx
<Message from="assistant">
  <Sources>
    <SourcesTrigger count={sources.length} />
    <SourcesContent>{sources.map(s => <Source href={s.url} title={s.title} key={s.url} />)}</SourcesContent>
  </Sources>

  <Reasoning isStreaming={isReasoning}>
    <ReasoningTrigger />
    <ReasoningContent>{reasoningText}</ReasoningContent>
  </Reasoning>

  <Tool defaultOpen={false}>
    <ToolHeader state={tool.state} type="tool-search_kb" />
    <ToolContent>
      <ToolInput input={tool.input} />
      <ToolOutput errorText={tool.errorText} output={tool.output} />
    </ToolContent>
  </Tool>

  <MessageContent><MessageResponse>{text}</MessageResponse></MessageContent>

  <MessageToolbar>
    <MessageBranchSelector>…</MessageBranchSelector>
    <MessageActions>
      <MessageAction label="Regenerate" tooltip="Regenerate response">…</MessageAction>
    </MessageActions>
  </MessageToolbar>
</Message>
```

**Порядок слоёв в ответе ассистента фиксирован:**
`Sources` → `Reasoning` → `Tool` → `MessageContent` → `MessageToolbar`.

## 6. Рабочее место поставщика («Тендерный юрист»)

Макет — [mockup/supplier-workspace.html](mockup/supplier-workspace.html), приложение — `web/`. Раскладка как у мессенджера
с карточкой собеседника, плотная: всё на своих местах, путь по закупке виден без подсказок. Экран собран из островов:
каждый смысловой блок — отдельная карточка на холсте, по ним и ориентируются.

**Главное правило — пользователь всегда видит, где он и что делать дальше.**

- **Путь по закупке — три шага по порядку**: 1 «Требования» → 2 «Техническое предложение» → 3 «Проверка заявки», потом
  подача на площадке. Шаги — вместо вкладок: номер или галочка, название и статус словами под ним
  («выписаны: 20 пунктов», «впишите 2 пункта», «4 ошибки», «ошибок нет»). Между шагами — шеврон. «Поиск», «Цена» и
  «Вопросы» — не шаги, а инструменты: стоят справа отдельно. Модель шагов одна на всё приложение: `web/src/lib/steps.ts` (`stepsOf`, `stageOf`).
- **«Поиск»** — по словам во всех документах закупки, без ИИ (`web/src/lib/doc-search.ts`). Окончания не важны: слово
  ищется по основе, «гарантия» найдёт «гарантией»; «ё» и «е» — одна буква. Фраза ищется целиком, а если её нет —
  значимые слова по отдельности. Результат — остров на документ: отрывки с подсветкой, «Показать больше текста».
  В прототипе поиска пока нет.
- **«Цена»** — до какой цены снижаться, без ИИ (`web/src/lib/price-floor.ts`): нижняя цена, при которой контракт
  не в убытке, с налогом с выручки, стоимостью обеспечения исполнения и антидемпинговыми мерами ст. 37 44-ФЗ.
  Сверху — остров «Ваши цифры»: начальная цена (из сведений о закупке), себестоимость, налог с выручки — три поля
  в ряд с ширины 600 px. Дальше «Проверить свою цену»: поле «Ваша цена», прибыль по ней (пока цены нет — по начальной)
  и **шкала цены** (`web/src/components/price-scale.tsx`, геометрия — `web/src/lib/price-scale.ts`). Шкала — от начальной
  цены вниз, кратно 10 %: зона убытка — бледная заливка `--danger`, без убытка — `--ok-tint`, у каждой иконка и подпись
  (подпись прячется, если зона уже неё, — container query, не обрезка); между зонами — зазор 2 px, над ним — «Нижняя
  цена» (нажатие ставит её вашей ценой); тонкая янтарная полоса под шкалой — где обеспечение повышенное (снижение
  на 25 % и больше), с легендой. Ваша цена — круглая ручка 16 с кольцом 2 px; ползунок поверх — обычный
  `input type=range`, прозрачный, с бегунком в 1 px, поэтому работают клавиши, диктор и касание. Масштаб шкалы зависит
  только от расчёта, не от вашей цены — иначе шкала ездила бы под пальцем; цена за краем прижимается к краю.
  Мышью над шкалой — цена под курсором и что по ней останется. Под шкалой — «Из чего складывается цена» ссылкой
  со стрелкой: таблица (нижняя цена и ваша рядом — табличная замена шкалы) открывается по нажатию. Последний остров —
  «Что ещё влияет на цену»: расходы на участие, обеспечение исполнения, антидемпинговые меры. Он свёрнут, под
  названием — сводка, что учтено («Расходы на участие 2 000 ₽ · обеспечение 5 % — гарантия · антидемпинговые меры»);
  открыт сразу, если без пользователя расчёт неполный — обеспечение есть, а ставки или срока нет (сводка тогда янтарная).
  Ответ — плавающим островом внизу, как «Скачать ТП». Процент обеспечения и закупку у малого бизнеса подставляет
  из требований. Подписи галочек короткие («Освобождены от обеспечения»), условия и статьи — в подсказке «?».
- **Вход в «Цену» заметен**: на шаге «Требования» первым, над «Кто может участвовать» (в приложении пока после групп), —
  остров «Перед торгами · До какой цены снижаться»
  (значок калькулятора на `--brand-tint`, ответ, если уже посчитан, и та же шкала без ползунка) с кнопкой «Открыть
  расчёт»; в строке шагов у «Цены» значок цвета бренда; в «Сведениях» под начальной ценой — ссылка «До какой цены
  снижаться». В прототипе — всё то же на примерах закупок.
- **«Как оценят заявку»** — на шаге «Требования» после «Кто может участвовать». Подпись под названием отвечает на
  первый вопрос конкурса: «Побеждает больше баллов из 100: цена — до 60 баллов, остальное — до 40» (в аукционе —
  «Побеждает наименьшая цена — баллов нет»). Дальше — строки, за которые дают баллы, по критериям: критерий без
  показателей (цена) — одной строкой, у остальных — подпись капсом (`eyebrow`, справа «всего до 30 баллов») и строки
  показателей. Строка: название (детализирующий показатель, под ним серым — показатель), бейдж `--brand-tint`
  «до 15 баллов», «Как считают», «Что приложить», «Форма» — серой меткой и текстом 14/20, ссылка на цитату из
  порядка оценки. Баллы — доля строки в итоговой сотне: значимость критерия × показателя × детализирующего;
  считает код (`web/src/lib/criteria.ts`), модель только переписывает значимости из документа. Значимость не указана
  у нескольких пунктов — вместо баллов то, что написано в документе. Значимости критериев в сумме не 100 % — янтарная
  строка «сверьте с порядком оценки». Цветной диаграммы долей нет: цвета статусов для неё не годятся. Числа и единицы
  («20 %», «3 000 000 ₽») не разрываются переносом. В приложении — `web/src/components/criteria-island.tsx`,
  в прототипе — `criteriaHTML()`.
- **Состав исполнителей** — если ТЗ требует назвать людей (ФИО, звание), в ТП после пунктов ТЗ — остров «Состав
  исполнителей». Справочника нет: состав от закупки к закупке свой. Кто нужен, выписывает ИИ — позиции, сколько
  человек, звание, с цитатой из ТЗ; людей вписывает участник, ИИ фамилий не видит и не придумывает. Строка — ФИО
  и звание, «Добавить музыканта», убрать строку. Над строками — сверка с ТЗ по каждой позиции: строка статуса с иконкой
  («Вокалист со званием не ниже заслуженного артиста — есть»), у неподходящего звания — пометка под строкой.
  «Вставить списком» — по человеку в строке, раскладывается без ИИ: по роли, если она названа; человек со званием — туда,
  где звание нужно; остальные по порядку, лишние — новыми строками. При наборе фамилии — подсказки из прошлых закупок
  вместе со званием, при наборе звания — обычные почётные звания. Незаполненный состав — ещё один пункт в «впишите
  N пунктов»; в файле ТП — таблица «Состав исполнителей». Внизу — условие проекта контракта о замене исполнителей
  со ссылкой на пункт. Фамилия того, кто подписывает заявку, среди исполнителей — предупреждение: ТП подают анонимно.
  В приложении — `web/src/components/cast-panel.tsx`, логика — `web/src/lib/cast.ts` (тесты — `cast.test.ts`);
  заготовку ИИ выписывает вместе с черновиком ТП (`cast` в `TpDraftSchema`), подсказки берутся из составов
  других закупок в браузере. Пример — «Педагог года» (ТЗ, п. 3.5); пример, сохранённый в браузере раньше,
  обновляется при открытии (`SAMPLE_VERSION` в `sample-purchase.ts`).
- **Подсказка «?»** — кнопка 28×28 с иконкой `help` 16 рядом с подписью поля, у термина или условия со статьёй
  закона. Карточка поверх: заголовок (t-strong) и текст (t-body), `--card`, скругление 12, тень `--float`,
  ширина до 320 px; над кнопкой, а если сверху нет места — под ней. Мышью открывается наведением (задержка 150 мс)
  и закрывается, когда мышь уходит с кнопки и карточки; нажатие закрепляет карточку. На телефоне наведения нет — там,
  как и с клавиатуры (Enter, пробел), открывается нажатием. Закрывается Esc, нажатием мимо, прокруткой. Короткая строка под полем остаётся,
  только если она про это поле сейчас («Из сведений о закупке», «В требованиях: …»); объяснения и статьи — в подсказку.
  Где стоит: калькулятор цены, реквизиты (КПП, ОГРН, ОКВЭД, МСП, НДС, счета, БИК, руководитель). В приложении —
  `web/src/components/hint.tsx` (Popover из Base UI), в прототипе — `hintBtn()` и одна карточка `#hint-pop`.
- **После аудита** (`AUDIT.md`): при первом входе — экран «Перед началом» с двумя галочками, не отмеченными заранее:
  согласие на обработку и отдельное согласие на передачу за рубеж, без обеих «Продолжить» неактивна. Под каждой
  загрузкой — выключатель «Распознавать сканы и фото через ИИ» с предупреждением, что картинка уходит как есть.
  Внизу «Реквизитов» — острова «Копия данных» (сохранить и загрузить файлом; загрузка только добавляет недостающее)
  и «Удалить все данные» (ссылкой, подтверждение с фокусом на «Отмена»). Номера реквизитов проверяются по длине
  и контрольным цифрам — янтарная строка под полем, когда из него ушли. В прототипе копия не скачивается
  и не читается, правовые документы — выжимкой в окне, полные шаблоны — в приложении.
- **«Дальше»** — в конце каждого шага: блок «Дальше — шаг 2 из 3 · Техническое предложение» с кнопкой;
  у ТП — кнопка «Дальше: проверка заявки» рядом со «Скачать»; после проверки без ошибок — «Готово к подаче», срок
  и кнопка «Скачать документы заявки».
- **Документы заявки — в одном окне** (прототип и приложение — `components/application-files.tsx`): кнопка «Скачать
  заявку» в шапке закупки, «Готово к подаче» в конце шагов и дело «Скачать документы и подать заявку» на главной
  (ссылка `…#files`) открывают окно. Состав заявки у каждой закупки свой, поэтому в окне два блока:
  1. «Файлы, которые пишу я» — ТП, анкета, декларация, предложение о цене, сведения об опыте и о специалистах,
     каждый файлом Word. Строка — название, откуда данные, статус бейджем («впишите 3 пункта», «впишите реквизиты»,
     «готово») и «Скачать»; ТП не составлено — «Составить». Внизу «Скачать всё архивом»: недостающие части пишутся
     по очереди, архив «Закупка — заявка.zip» собирает сервер (`api/tp/zip`), файлы пронумерованы по порядку.
  2. «Что требует заказчик» (пока только в приложении) — все пункты «Что подать» из требований с цитатой и галочкой
     «готово»: выписки, лицензии, обеспечение и остальное, что участник собирает сам. Отметки хранятся в закупке
     по тексту пункта. Сопоставлять пункты с файлами блока 1 не пытаемся: ошибка спрятала бы нужный документ.
  Заявку не проверяли — ссылка на шаг 3. Из предпросмотра файла (прототип) — «К документам заявки».
- **Сведения об опыте и о специалистах** — ещё две части заявки, только если за них дают баллы по порядку оценки
  (`partsOf(form, criteria)`). Их пишет ИИ по форме заказчика из «Опыта: договоров и актов» и «Сотрудников:
  квалификации» — это не образцы оформления, а сами сведения, от каждого документа — начало и конец. В строку
  попадает только то, что засчитают. Под названием части — ожидаемые баллы по шкале из порядка оценки («≈ 59 баллов
  показателя — 8,8 из 100 итоговых»), ниже янтарём — что не засчитают и чего не хватает до максимума. Своих
  документов нет — подсказка янтарная: «загрузите … иначе баллов не будет». В «Документах заявки» бейдж — баллы
  («8,8 из 15 баллов»). Без ИИ и в примере — таблица с полями для заполнения.
- **Статус закупки в списках — бейджем со словами**: пилюля с бледной заливкой статуса, текст и иконка его цветом —
  «составить ТП», «ТП: впишите 2 пункта», «4 ошибки», «готово к подаче», «приём закончился». Срок — тоже бейджем:
  «5 дней» янтарём за неделю и меньше, дальше серым. Цвета без слов нет. Тоны: индиго — ваш следующий шаг,
  янтарь — нужны ваши данные или срок близко, красный — ошибка, зелёный — готово, серый — справка (`badge`,
  `stageBadge`, `dueBadge` в прототипе; в приложении — `components/badge.tsx` и `lib/home.ts`, пока на главной).
  В списке закупок приложения статус пока строкой «Шаг 2 · ТП: впишите 2 пункта» (`stageOf`). Красная заливка —
  `--danger-tint`, 8 % красного: текст `--danger` на ней 4,5:1 и в светлой, и в тёмной теме.
- **Кнопки с подписями**: «Скачать заявку», «Добавить документы», «Сведения». Не помещаются в шапке закупки —
  сначала без подписей «Добавить документы» и «Сведения» (узкий остров, меньше 820), потом все (меньше 560) —
  иконка с подписью для диктора. Подзаголовок со сроком не обрезается, а переносится на вторую строку.
- **Уведомления** (прототип): колокольчик в шапке каждого экрана, число новых — пилюлей бренда на углу. Нажатие —
  всплывающий остров с тенью `--float`: ответы юриста, «До подачи N дней», «Приём заявок закончился». Новое — жирным
  и с точкой бренда, «Прочитать все». Нажатие на уведомление ведёт туда, о чём оно. Esc и клик мимо закрывают.
  Копии — письмом на почту из «Реквизитов».
- **Вопросы юристу** (прототип): раздел в меню с числом новых ответов. Живой юрист по закупкам отвечает в течение
  рабочего дня. «Спросить юриста» под ответом ИИ и в итоге проверки открывает окно: закупка, что приложить (ответ ИИ
  или итог проверки), вопрос. Раздел — как закупки: список вопросов **288** и разговор; статусы бейджем «ждёт ответа»,
  «новый ответ», «юрист ответил». Ответ юриста подписан именем и ролью с аватаром — его не спутать с ответом ИИ.
  Ответил — число в меню, уведомление, дело «Прочитать ответ юриста» на главной сразу после самого срочного и письмо.
- **Острова.** Холст `--canvas`, на нём острова: белая карточка `--card`, радиус 16, кольцо 1 px и мягкая тень
  (`--island-shadow`). Между островами и у краёв окна — 8 px холста. Остров — это один смысловой блок: сайдбар,
  список закупок, шапка закупки с шагами, каждая группа требований, товары ТП, итог проверки, «Дальше», разговор.
  Стиль взят из карточки меню AI Elements в Figma — [OpenInContent](https://www.figma.com/design/NDctJTjd4iyzeT9zWg3WwZ/AI-Elements---%E2%96%B2-Vercel--Community---Copy-?node-id=2004-14774):
  кольцо `0 0 0 1px` 10% чёрного, тень `shadow-lg`, пункты с отступом 4–8 и скруглением 8. Полную тень lg (`--float`)
  носят только всплывающие острова: выезжающее меню, лист «Сведения» поверх закупки, плавающая панель «Скачать ТП»,
  окна. У неподвижных тень мягче — иначе всё «летает» и иерархия пропадает.
- **Заголовок острова** — без черты под ним: название 14/20, счётчик, справа одно действие. Пояснение к шагу и
  подписи — прямо на холсте, по краю текста в островах. Плашка на холсте — отдельным блоком со скруглением 16,
  внутри острова — 10.
- **Сайдбар 224** — разделы: Главная, Закупки, Спросить про тендер, Вопросы юристу; группа «Данные компании» (Реквизиты, Образцы
  и реквизиты); внизу «Как это работает» и карточка участника. «Образцы и реквизиты» — по делу раздела: прошлые заявки
  служат образцами, из анкет и карточки предприятия заполняются реквизиты; и не путается с документами закупки.
  Группы — по видам документов, у каждой подпись, зачем она: ТП, анкеты, декларации, предложения о цене, письма и
  описи, документы компании, «Опыт: договоры и акты» и «Сотрудники: квалификация» (для баллов в конкурсах), «Другое».
- **Шапка экрана 64** на холсте (8 сверху + 56): заголовок 20/28 на одной линии со знаком в сайдбаре и по левому краю
  островов, в той же строке — подзаголовок с главной цифрой экрана. Справа — одно главное действие. Справа шапка,
  шапка закупки и прокручиваемые острова оставляют одинаковое место под полосу прокрутки (`scrollbar-gutter: stable`) —
  правые края кнопки и островов совпадают и там, где полоса занимает место (в Chromium тонкая полоса — 10 px).
- **Закупки** — три столбца островов: список **288** (поиск; строки: значок закона «44»/«223», название,
  заказчик, статус шага словами; справа дни до подачи) | закупка (остров-шапка со сроком словами и шагами, под ним
  острова шага) | сведения **272** (острова «О закупке», «Документы закупки» с пометками «со скана» и «не прочитан»,
  удаление). Столбцы прокручиваются каждый сам; разговор — один остров с полем ввода внизу; «Скачать ТП» — плавающий
  остров внизу шага.
- **Подписи в строке шагов сокращаются по месту**: строка мерится, и если не помещается — сначала «ТП», потом
  «Проверка», потом у «Поиска», «Цены» и «Вопросов» остаются значки, в последнюю очередь пропадают стрелки между
  шагами (порядок видно по номерам). Ширина зависит от статусов шагов и счётчика вопросов, поэтому пороги по ширине
  панели не годятся. Диктор всегда читает полное название. Не помещается и так (телефон) — «Поиск», «Цена» и
  «Вопросы» с подписями уходят на свою строку, а шаги листаются отдельно, текущий прокручен на виду.
- **Точки перелома.** От 1560 — три столбца. 1180–1559 — список и закупка, сведения открываются кнопкой листом
  поверх закупки (те же острова на холсте). До 1180 — один столбец: список или закупка с кнопкой «назад».
  До 1024 сайдбар выезжает островом с отступом 8 по кнопке меню.
- **Главная — рабочий стол в одну колонку, три острова по важности** (прототип и приложение: `app/page.tsx`,
  что показать — `lib/home.ts`):
  1. «Сейчас важно» — самое срочное дело поверхностью `--paper-2` внутри острова: бейдж срока первым, название 16/24,
     «закупка · заказчик» и **единственная заливная кнопка экрана** («Открыть ТП», «Открыть проверку», «Открыть
     требования», «Скачать документы» — окно «Документы заявки») — ведёт сразу в нужный шаг. Остальные дела — строками
     по сроку подачи: цветная точка (индиго — ваш
     шаг, янтарь — данные или скан, красный — ошибка), название, закупка, бейдж срока. Дел нет — «всё сделано».
  2. «Закупки по этапам» — четыре плашки: «Техническое предложение», «Проверка заявки», «Готово к подаче», «Приём
     закончился»; число моноширинным 20 и что на этапе ждёт вас. Этап не двигают руками — он следует из шагов
     и срока (`laneOf`). Нажатие на этап оставляет в таблице только его закупки (`aria-pressed`, повторное — сброс).
     Таблица: закон, название и заказчик, «Что сейчас» (бейдж этапа), «До подачи» (бейдж срока). На узком острове
     бейджи уходят под название, этапы — строками по 44.
  3. «Данные компании» — реквизиты (полоса заполнения, бейдж «не хватает N полей») и образцы ТП. Реквизиты — не дело
     в списке: вписываются один раз.
  «Новая закупка» в шапке главной — кнопкой с обводкой, пока в содержимом есть своя главная кнопка. Вопросов на главной
  нет: они в разделе «Спросить про тендер» и во вкладке «Вопросы» закупки. Новому пользователю вместо дел и этапов —
  «С чего начать»: три шага и одна кнопка «Загрузить документы закупки». Разбор с источниками —
  [артефакт «Разбор главной поставщика»](https://claude.ai/artifact/FwzwcqAeJKzpZGZ1t975FB).
- **«Как это работает»** — карта приложения: путь по закупке с тем, где нажимать; что лежит в каждом разделе;
  что значат цвета (индиго — следующий шаг, янтарный — нужно действие или срок близко, красный — ошибка, зелёный
  с галочкой — сделано, серый — справка или не начато).
- **Внутри островов** два вида списков. Навигация (меню, список закупок, дела в «Сейчас важно», разделы) — пункты
  как в карточке меню: скругление 8, подсветка при наведении, открытый — индиго-тинт `--select`, разделителей нет.
  Содержимое (требования, пункты ТП, ошибки проверки, документы) — строки с разделителями `--line` с отступом от краёв.
  Несколько предупреждений — одна плашка со списком. Ссылки на источник — чипы с иконкой.
- **Шкала шрифтов** — токены `--t-*` из [brand.css](brand.css), пять кеглей с интерлиньяжем, кратным 4:

  | Роль | Кегль | Где |
  |---|---|---|
  | `--t-page` | 20/28, 700 | заголовок экрана: «Закупки», «Главная» |
  | `--t-title` | 16/24, 600 | открытая закупка, заголовок разговора, итог проверки |
  | `--t-section` / `--t-doc` / `--t-read` | 14/20 — 600 / 500 / 500 | заголовки панелей и пунктов ТП / текст ТП и поля ввода / текст требований и цитаты |
  | `--t-body` / `--t-strong` / `--t-label` | 13/20 — 500 / 600 / 500 | текст интерфейса / названия в списках / меню и шаги |
  | `--t-caption` / `--t-over` / `--t-num` | 12/16 | подписи и статусы / надписи капсом / счётчики и сроки |

  Интерфейс — 13, содержимое — 14: текст документа чуть крупнее обвязки. Второстепенное — серым `--ink-3`, а не мельче.
- **Высоты и поля** — кнопка и поле 32, пункт меню 32, шапка экрана 64 (56 на телефоне), шапка закупки 56, пункт-шаг 44;
  поля внутри острова 16 (на телефоне 12), между островами 8, шаг отступов 4.
- Источники: кегли 12/16, 14/20, 16/24 и 20/28 — как в шкале [Carbon](https://github.com/carbon-design-system/carbon/blob/main/packages/type/src/styles.ts)
  (сверено по исходнику); 13/20 для интерфейса добавлен ради плотности. Принцип «выделять ослабляя» —
  из [Refactoring UI](https://medium.com/refactoring-ui/7-practical-tips-for-cheating-at-design-40c736799886).

## Правила системы

**Сообщения**

1. Пользователь — бабл `--secondary`, справа, максимум ~80% ширины.
   Ассистент — без фона, во всю ширину. Не давать ассистенту бабл.
2. Тело сообщения всегда `text-sm` (14/20). `text-base` (16) — только в поле ввода.
3. Аватарок в системе нет: роль читается по выравниванию и наличию фона.

**Цвет**

4. `--primary` (синий `#155dfc`) применяется скупо: кнопка отправки и ссылки на источники.
   Всё остальное — нейтральная шкала.
5. Всё второстепенное — `--muted-foreground`: reasoning, счётчики, подписи кнопок в подвале ввода,
   имена моделей, плейсхолдеры.
6. Разделители и рамки — `--border`; рамка поля ввода — `--input`.
   В тёмной теме оба полупрозрачно-белые, не серые.

**Размеры и ритм**

7. Иконочная кнопка в плотных зонах (тулбар сообщения, подвал ввода) — **28×28**, иконка 16,
   `rounded-md (8)`. Отдельно стоящая — 32×32.
8. Иконка рядом с текстом в подвале ввода — **14**, а не 16.
9. Базовый радиус — 10 (`rounded-lg`): поле ввода, бабл сообщения, плитка вложения.
   Кнопки и чипы — 8 (`rounded-md`). Мелкие превью — 4.
10. Шаг сетки — 4. Реально используемые отступы: 4, 6, 8, 10, 12, 16, 20.

**Состояния**

11. `PromptInputSubmit.status` отражает жизненный цикл запроса:
    `ready` → `submitted` → `streaming` → `error`. Иконка и поведение меняются сами.
12. Сворачиваемые блоки открыты по-разному по умолчанию:
    `Reasoning` — **открыт**, `Task` — **открыт**, `ChainOfThought` — **закрыт**, `Tool` — по `defaultOpen`.
13. Во время стриминга: `Reasoning` раскрывается сам и закрывается по завершении;
    у `Plan` заголовок и описание получают `Shimmer`.
14. Hover-состояния нарисованы для всех интерактивных элементов
    (`MessageAction`, `PromptInputButton`, `ReasoningTrigger`) — не пропускать их при реализации.

**Доступность**

15. `MessageAction` требует `label` для скринридера, даже когда задан `tooltip`.
16. Числа в счётчике веток (`1 of 3`) — табличные цифры, чтобы не прыгала ширина.

## Чего в системе нет

Нет аватаров, нет таймстампов сообщений, нет индикатора «печатает…» в виде трёх точек
(вместо него — `Shimmer` и статусы `PromptInputSubmit`), нет непрочитанных и статусов доставки.
Для чата поддержки всё это придётся добавлять поверх — и делать это в той же токен-системе:
`text-xs` + `--muted-foreground` для метаданных, 28px для иконочных кнопок.
