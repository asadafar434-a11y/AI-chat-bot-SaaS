# Что в существующем домене переписывать нельзя

## 1. Правило

Бизнес-логика `web/src/lib` — проверенный актив. Она покрыта тестами, отражает правила 44-ФЗ/223-ФЗ и
накоплена итерациями. **Перенос на серверную архитектуру не является поводом её переписывать.**

Следствия:

1. Доменный код переносится в сервер как есть, а не переписывается под новую архитектуру.
2. Инфраструктура добавляется **снаружи** домена и внедряется через адаптеры.
3. Любая правка домена — отдельная задача с отдельным обоснованием, а не часть переноса на БД.
4. Критерий «ничего не сломалось» — текущие 508 тестов остаются зелёными.

## 2. Граница доступа к браузерному хранилищу

IndexedDB касаются **ровно семи** модулей. Это и есть поверхность, которую предстоит заменить адаптерами:

| Модуль | Роль | Что с ним будет |
|---|---|---|
| `web/src/lib/db.ts` | низкоуровневый доступ к трём базам IndexedDB | заменяется на реализацию доступа к серверу; формат данных сохраняется |
| `web/src/lib/purchase-store.ts` | чтение/запись закупок и их документов | заменяется на серверный источник |
| `web/src/lib/evidence-store.ts` | чтение/запись фактов базы доказательств | заменяется на серверный источник |
| `web/src/lib/me-store.ts` | реквизиты и образцы участника | заменяется на серверный источник |
| `web/src/lib/use-purchases.ts` | React-хук подписки на изменения | сохраняет интерфейс, меняется источник |
| `web/src/lib/backup.ts` | чтение баз для выгрузки копии | **сохраняется**: это инструмент переноса и восстановления |
| `web/src/lib/wipe.ts` | «удалить все мои данные» | сохраняется в браузере; серверный аналог — tenant-scoped и аудируемый |

Плюс один компонент: `web/src/components/side-nav.tsx:23` читает базу напрямую.

**Ни один из этих модулей не является доменной логикой.** Это хранилище. Именно его меняем — домен
остаётся.

Формат записей версионируется в шести точках (`fromStore`/`toStore`): `purchase-provider.tsx:7`,
`backup-format.ts:1`, `evidence-store.ts:1`, `me-store.ts:1`, `purchase-store.ts:1`, `use-purchases.ts:4`.
Механизм `data-format.ts` сохраняется целиком, включая защиту `NewerDataError`.

### Что означает «без изменений» конкретно

| Требование | Следствие |
|---|---|
| Функции остаются детерминированными | не добавлять внутри домена `Date.now()` там, где сейчас передаётся `now` (например, `makeFact(input, now, id)` в `evidence-base.ts:175`) |
| Форма данных не меняется | `Profile` остаётся объектом из 20 строк, `Purchase` — объектом, `Fact` — объектом с union-источником; отсюда решение `JSONB` в [data-model.md](data-model.md) |
| Ошибки остаются типизированными | `NewerDataError`, `errorText`, `http-error` не меняются |
| Тесты остаются зелёными | 508 тестов — регрессионная сетка всего этапа |

## 4. Разделение профиля не трогает домен

На сервере корпоративные реквизиты и персональные данные лежат в разных таблицах
([data-model.md](data-model.md) §4), но домен по-прежнему получает **один объект `Profile` из 20 полей**.
Это достигается одной точкой сборки вне домена:

```
OrganizationProfile.fields (15 корпоративных полей)
UserProfile.fields        (5 персональных полей)
            │
            └── assembleProfile()  ← вне web/src/lib, в слое backend
                    │
                    └── Profile { 20 ключей }  → домен без изменений
```

| Правило | Значение |
|---|---|
| Точка сборки одна | ровно один модуль в слое backend; в домене новых функций не появляется |
| Приоритет при пересечении ключей | `OrganizationProfile`; факт подмены пишется в лог как диагностика |
| Проверка полноты | собранный объект сверяется с `PROFILE_KEYS` (`web/src/lib/profile.ts`); недостающие ключи приводятся к `EMPTY_PROFILE`, лишние отбрасываются с записью в лог |
| Обратная сборка | при сохранении изменения объект `Profile` делится обратно на две таблицы тем же модулем |
| Тесты домена | проходят как раньше: `profile.test.ts` не видит разделения, он работает с объектом |

Следствие: разделение реквизитов и персональных данных — это изменение **схемы хранения**, а не домена.
Ни один модуль из раздела 3 не правится.

## 5. Что считается переписыванием и запрещено

| Запрещено | Почему |
|---|---|
| Переносить правила 44-ФЗ/223-ФЗ в SQL-запросы или в код БД | логика должна остаться в одном месте и быть покрыта тестами |
| Менять тип `Purchase` при переносе в `payload` | 508 тестов перестанут соответствовать реальности |
| Заменять доменные функции на «упрощённые» версии ради сервера | тихая потеря поведения |
| Выносить правила в отдельную «новую» папку домена параллельно старой | два источника правды, расхождение поведения |
| Менять `data-format.ts` при переносе данных | сломает версионирование записей и защиту от порчи |
| Править `access.ts`, `proxy.ts`, route handlers на этом этапе | вне зафиксированного контракта |
| Разбивать `Profile` на два типа в домене | разделение — вопрос хранения; домен продолжает работать с объектом из 20 полей (§4) |

## 6. Что разрешено делать с доменом

| Разрешено | Условие |
|---|---|
| Добавить рядом новый модуль, если старая функция не подходит | существующая функция остаётся и используется |
| Внедрить зависимость через параметр функции | сигнатура по умолчанию не меняется, тесты продолжают работать |
| Обёрнуть доменную функцию сервисом | доменный код не знает про БД, сеть и провайдера |
| Исправить явную ошибку | отдельная задача, отдельные тесты, отдельное обоснование |
| Добавить тест | только увеличение покрытия, не ослабление проверок |

## 7. Ограничения поверхности, важные для проектирования

| Наблюдение | Следствие для архитектуры |
|---|---|
| Тексты документов приходят в теле HTTP-запроса с браузера | маршруты ИИ можно оставить как есть; перенос хранения их не ломает |
| `purchase.parts`, `tp`, `tpDraft`, `chat` встроены в закупку | решение `payload = JSONB` сохраняет форму и избегает нормализации непроверенного кода |
| `unreadable: FailedFile[]` хранится в закупке | при переносе ошибки чтения остаются в `payload`, статус переносится в `Document.readError` |
| Суммы хранятся числами (`tpPrice`, `measures.value`) | денежные значения платежей — только целые копейки (`amountMinor`); в домене форма не меняется, граница проходит на backend |
| Даты — строки `ГГГГ-ММ-ДД` | колонки типа `Date` вводятся только там, где формат уже ISO; для `Validity` используется `Json`, см. [data-model.md](data-model.md) §3.8 |
| `DocStamp[]` — отпечатки содержимого | остаются в `payload`; отдельная таблица отпечатков не нужна |
| `Profile` — один объект из 20 полей, объединяющий корпоративное и персональное | разделение выполняется в backend одной функцией сборки (§4), форма объекта в домене неизменна |
