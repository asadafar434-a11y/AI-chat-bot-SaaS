# Порядок этапов, перенос данных из IndexedDB и стратегия отката

## 1. Абсолютные ограничения

Эти правила не обсуждаются и не обходятся ни на одном этапе:

1. **IndexedDB остаётся источником истины до отдельной подписи на переключение.**
2. **Запрещено** удалять, очищать, сбрасывать, перезаписывать или инвалидировать данные браузера.
   В том числе запрещено вызывать `deleteDatabases()` (`web/src/lib/db.ts:84`) и логику `wipe.ts`
   в рамках переноса.
3. Никакая необратимая миграция БД без процедуры отката.
4. Перенос всегда повторяемый или безопасно возобновляемый.
5. Числа до переноса и после обязаны совпасть; расхождение — повод остановиться, а не «посмотреть вручную».
6. Этап не начинается, пока предыдущий не подтверждён: на каждом этапе есть проверяемый результат, а не
   ощущение, что «вроде работает».

## 2. Порядок этапов

Этот порядок обязателен. Каждый следующий этап опирается на появившееся в предыдущих, и нарушение порядка
ломает откат и верификацию.

```
S0  Architecture Contract            ← этот документ
      ↓
S1  PostgreSQL foundation            Prisma, схема, репозитории с org-scope
      ↓
S2  Auth.js и tenancy                СЕССИИ, роли, приглашения, авторизация
      ↓
S3  Import/export миграция           экспорт из браузера + идемпотентный импорт
      ↓
S4  Server reads                     чтение с сервера за флагом + dual-read
      ↓
S5  Server writes                    запись на сервер
      ↓
S6  Storage                          S3: документы, тексты, доступ
      ↓
S7  Audit                            AuditEvent для важных изменений
      ↓
S8  Jobs                             pg-boss, распределённые лимиты
      ↓
S9  Backups / restore                PITR + проверенное восстановление
      ↓
S10 Payments                         ЮKassa
      ↓
S11 Final cutover                    подпись, легаси уходит в read-only
```

Обоснование порядка:

| Переход | Почему именно так |
|---|---|
| S1 → S2 | серверные сессии физически хранятся в БД: без S1 нет таблицы `Session` и адаптера, Auth.js не появляется |
| S2 → S3 | перенос выполняется пользователем, у которого уже есть организация и вход, иначе перенесённые данные некуда привязать |
| S3 → S4 | сначала данные должны лежать в БД, и только потом на них переключается чтение |
| S4 → S5 | запись на сервер без проверенного чтения означает запись в место, откуда данные ещё не читают |
| S5 → S6 | метаданные документов уже созданы в S1 и заполняются на S5; содержимое выносится в S3/S6, когда есть надёжная запись строк |
| S6 → S7 | аудит пишется на те же операции, что и работа с файлами; без стабильного хранилища события «скачал» неполны |
| S7 → S8 | фоновые задачи порождают изменения — аудит должен уже быть, иначе изменения останутся неучтёнными |
| S8 → S9 | очередь pg-boss лежит в той же БД, что и данные: резервное копирование обязано покрывать её **до** того, как в неё начнут класть задачи |
| S9 → S10 | платежи не запускаются, пока не существует проверенное восстановление: потеря базы тогда означает потерю денег |
| S10 → S11 | финальное переключение делается только после того, как работает всё, включая биллинг |

## 3. Этапы и откат

Откат указывается для каждого этапа. «Откат не требуется» допустимо только там, где этап ничего не меняет
вне документации.

### S0. Архитектурный контракт

| | |
|---|---|
| Содержание | документы `docs/stage-11/*` |
| Результат проверяется | документы приняты; расхождения между ними отсутствуют |
| Откат | изменение документации; код не затронут |

### S1. Фундамент PostgreSQL

| | |
|---|---|
| Содержание | `prisma/schema.prisma`, аддитивная миграция только `CREATE`, клиент Prisma, слой репозиториев с обязательным `organizationId` |
| Таблицы | 11 прикладных таблиц ([data-model.md](data-model.md) §2.2) |
| Результат проверяется | миграция применяется на пустой БД; `npm test`, `build:host`, `check:host` зелёные; интеграционный тест пишет и читает строку с чужим `organizationId` и получает отказ |
| Откат | **полный, до исходного состояния.** Таблиц до S1 не было, поэтому миграция вниз (`DROP` созданных таблиц) ничего не теряет. Прикладной код на этом этапе не переключён на БД, значит после отката приложение работает как до этапа |
| Ограничение | только `CREATE`. Ни `DROP`, ни `ALTER ... NOT NULL`, ни переименований существующих таблиц |

### S2. Auth.js и tenancy

| | |
|---|---|
| Содержание | `User`, `Session`, `Account`, `VerificationToken`, `Invitation`; адаптер Auth.js; вход по email+паролю; приглашение и setup-flow; сброс пароля; `requireSession` / `requireMembership` / `requireRole` / `withOrgScope` |
| Таблицы | +4 ([data-model.md](data-model.md) §2.3) |
| Результат проверяется | вход, приглашение, принятие приглашения, сброс пароля работают; `member` не может пригласить; доступ к чужой организации отклоняется; вход по `ACCESS_PASSWORD` продолжает работать (переходный период) |
| Откат | **полный, до состояния S1.** Удаляются 4 добавленные таблицы, откатывается код входа. S1 не затрагивается, данные S1 сохраняются. Сессии и приглашения — производные сущности, потеря их при откате не является потерей бизнес-данных |
| Ограничение | `ACCESS_PASSWORD` и `tl_access` обязаны остаться рабочими на этом этапе, иначе падает `check:host` (риск R7) |

### S3. Перенос данных: экспорт и импорт

| | |
|---|---|
| Содержание | выгрузка копии формата `tender-lawyer-backup` v1 из браузера; идемпотентный импорт в БД; сводка со счётчиками и агрегатами |
| Результат проверяется | `source_count == target_count` по каждому хранилищу **и** совпадение агрегатов; повторный запуск не создаёт дублей; прерванный импорт возобновляется |
| Откат | удалить содержимое **тестовой** БД и повторить. Браузерные данные не участвуют и не изменяются. На production-данных откат означает удаление только перенесённых записей по `legacyId`, что безопасно, поскольку они производны от копии |
| Ограничение | экспорт снимается **до** любых изменений в приложении; копия хранится вне репозитория |

### S4. Чтение с сервера за флагом

| | |
|---|---|
| Содержание | чтение через репозитории за флагом конфигурации; затем dual-read — сверка ответов сервера и браузера |
| Результат проверяется | доля расхождений dual-read ниже согласованного порога; список расхождений разобран |
| Откат | **полный, одной переменной.** Флаг гасится, приложение возвращается к чтению из IndexedDB. Данные не потеряны: IndexedDB цел, записи на сервер ещё не велись |
| Ограничение | запись на сервер на этом этапе выключена |

### S5. Запись на сервер

| | |
|---|---|
| Содержание | новые изменения пишутся в PostgreSQL; браузерные данные переходят в режим read-only для восстановления |
| Результат проверяется | стабильный период без потерь; сверка показывает отсутствие дублей и потерь |
| Откат | **ограниченный, только в окне стабилизации.** Записи, сделанные на сервере после переключения, выгружаются обратно в браузер **до** отключения сервера. После закрытия окна откат возможен только отдельной задачей с новым ADR |
| Ограничение | это первый этап, на котором переход становится необратимым. Открывается он только после успешной верификации S4 |
| Окно стабилизации | длительность — открытый вопрос, см. [decisions-and-risks.md](decisions-and-risks.md) §3 |

### S6. Объектное хранилище S3

| | |
|---|---|
| Содержание | `StorageAdapter`; перенос исходных файлов и текстов в S3; выдача короткоживущих ссылок только после проверки доступа |
| Результат проверяется | бакет приватный; публичный доступ запрещён; шифрование в покое настроено там, где провайдер поддерживает; ключи org-scoped и непрозрачные; тест «чужой документ» возвращает отказ **и не создаёт ссылку**; ссылка перестаёт работать после истечения |
| Откат | приложение возвращается к хранению содержимого в `Purchase.payload`; строки `Document` остаются с заполненными метаданными. Объекты не удаляются при откате — они не мешают и могут быть использованы снова |
| Ограничение | до S9 бэкап объектов ещё не проверен, поэтому откат обязан сохранять объекты; удаление — только после проверки восстановления |

### S7. Аудит

| | |
|---|---|
| Содержание | запись `AuditEvent` на важные изменения: создание закупки, загрузка и скачивание документа, изменение фактов, приглашение и смена роли, смена пароля, стирание данных |
| Результат проверяется | каждое перечисленное действие оставляет событие; в `metadata` нет персональных данных и содержимого документов |
| Откат | **откат не требуется и не выполняется.** Журнал аудита — append-only; он не мешает работе и не влияет на данные. Отключение возможно только флагом, но потеря событий необратима, поэтому флаг не применяется без отдельного ADR |
| Ограничение | `AuditEvent` не содержит содержимого документов, ключей и токенов |

### S8. Фоновые задачи pg-boss

| | |
|---|---|
| Содержание | схема `pgboss`; процесс `worker`; перенос лимитов, бюджета ИИ и дедупликации из памяти процесса в PostgreSQL; только после этого — вторая реплика `app` |
| Результат проверяется | лимит срабатывает при двух экземплярах приложения; задача не создаёт дубль при повторе; очередь переживает перезапуск воркера |
| Откат | приложение возвращается к одной реплике `app`; счётчики в БД остаются, но не используются. Схема `pgboss` не удаляется — это управляемая pg-boss схема, её состав меняется вместе с версией |
| Ограничение | **до завершения S8 вторая реплика `app` запрещена.** Это блокер корректности, а не оптимизация (риск R1) |
| Порядок внутри этапа | S9 должен завершиться позже: очередь лежит в резервной копии БД, но отдельная проверка восстановления очереди обязательна |

### S9. Резервные копии и восстановление

| | |
|---|---|
| Содержание | непрерывный WAL-архив, ежедневные полные копии, копирование объектов в отдельный бакет, процедура и **выполненная** проверка восстановления |
| Результат проверяется | восстановление выполнено в отдельном контуре; тесты зелёные; счётчики совпадают с последним отчётом о переносе; дата и результат зафиксированы |
| Откат | откат не применим: копии не отменяют работу системы. Если проверка восстановления не пройдена, **предыдущие этапы не считаются готовыми к production** — это блокирующий результат, а не формальность |
| Ограничение | копия хранится **в РФ**, отдельно от основного хранилища; копия PostgreSQL и копия бакета — в разных сервисах |

| | |
|---|---|

## 4. Отображение хранилищ IndexedDB

| IndexedDB | → | Целевое место | Ключ переноса |
|---|---|---|---|
| `purchases` | → | `Purchase.payload` + колонки | `Purchase.legacyId` |
| `documents` (по `id` закупки) | → | `Document` (S1, заполняется на S5) + объекты S3 (S6) | `Document.legacyId = "{purchaseId}:{index}"` |
| `settings["profile"]` | → | `OrganizationProfile.fields` (15 корпоративных полей) **+** `UserProfile.fields` (5 персональных) | одна строка каждого профиля |
| `settings["profile-meta"]` | → | `OrganizationProfile.version` + `UserProfile.version` | |
| `samples` | → | `Sample` | `Sample.legacyId` |
| `facts` | → | `Fact` | `Fact.legacyId` |

Разделение профиля на два назначения — следствие решения D11a и подробно описано в
[data-model.md](data-model.md) §4. Оно не меняет формат копии: экспорт по-прежнему кладёт объект из 20
ключей, а **разделение выполняется при импорте**, на сервере.

Записи без `v` считаются форматом 1 — так же, как это делает существующий код. Версия сохраняется в
`originalFormatVersion` / `version` и не теряется.

Принадлежность реквизитов при переносе: одна исходная браузерная установка переносится в одну
организацию, решение фиксируется в `LegacyImportBatch`. Персональные пять полей достаются пользователю,
который их заполнил; корпоративные пятнадцать — организации.

## 5. Что уже готово и переиспользуется

Ключевая находка: **механизм переноса данных в проекте уже существует и покрыт тестами.** Строить новый
экспорт с нуля не нужно и запрещено — это потеря проверенной логики.

| Актив | Что даёт | Файл |
|---|---|---|
| Формат копии `tender-lawyer-backup` v1 | machine-readable экспорт всех пяти хранилищ | `web/src/lib/backup-format.ts:7-20` |
| `buildBackup` / `parseBackup` | сборка и строгая проверка копии | `web/src/lib/backup-format.ts:26-65` |
| `missingFrom` | **не затирающая** загрузка: добавляет только отсутствующее | `web/src/lib/backup-format.ts:76-86` |
| Версионирование записей `v` + миграции формата | приведение старых записей к текущему виду существующим кодом | `web/src/lib/data-format.ts:14-68` |
| Запрет читать записи новее приложения | защита от «старый код портит новые данные» | `data-format.ts:41-46` |
| Копии только реквизитов из настроек | тема/согласие/отметки не переносятся | `backup-format.ts:23` |

Следствие: перенос — это **чтение копии на сервере и запись в PostgreSQL идемпотентно**, без изменения
формата данных и без изменения доменного кода.

## 6. Что делает импорт идемпотентным

| Механизм | Как работает |
|---|---|
| Ключ идемпотентности | `legacyId` — исходный идентификатор из IndexedDB |
| Повторный запуск | запись с уже существующим `legacyId` не создаётся заново, а сверяется и обновляется |
| Батч | `LegacyImportBatch` с уникальным `batchKey`: повторный запуск того же батча не дублирует работу |
| Объекты S3 | ключ выводится из `legacyId`, повторная запись идёт в тот же ключ |
| Возобновляемость | прогресс по закупкам: уже перенесённые пропускаются, прерванный батч продолжается |
| Версии формата | приведение к текущему формату существующим `fromStore`, без новой логики |

## 7. Что делает перенос повторяемым и проверяемым

Для каждого запуска генерируются **два** артефакта:

1. **Машиночитаемый** — копия формата `tender-lawyer-backup` v1, пригодная для повторного импорта.
2. **Человекочитаемый** — сводка:

| Раздел сводки | Содержание |
|---|---|
| Период | время экспорта, время импорта |
| Счётчики | сколько записей в источнике, сколько прошло в цель, по каждому хранилищу |
| Контрольные суммы | sha256 каждого экспортированного документа и каждого текста |
| Агрегаты | сумма `tpPrice` по закупкам, число закупок с ТП, число подтверждённых фактов, число фактов со сроком, число закупок со слотами `unreadable` |
| Профили | сколько корпоративных и сколько персональных полей перенесено; расхождение с `PROFILE_KEYS` явно указывается |
| Потери | что не перенеслось и почему |
| Итог | `source_count == target_count` для каждого хранилища либо явная причина расхождения |

Критерий успеха: для каждого хранилища счётчик источника равен счётчику цели. Проверка агрегатов обязательна:
одинаковые счётчики при разных данных — это не перенос.

## 8. Проверочные сценарии

Согласно `AGENTS.md` §6 перенос тестируется на следующих наборах данных:

| Сценарий | Что проверяет |
|---|---|
| пустые данные | перенос не падает, нули на обоих концах |
| одна организация, один пользователь | базовый случай |
| несколько организаций | изоляция при переносе |
| записи, похожие друг на друга | нет склейки разных сущностей |
| отсутствующие необязательные поля | `null`/`undefined` не ломает импорт |
| повреждённые записи | битые записи не роняют батч, попадают в отчёт о потерях |
| документы с метаданными и без | корректность `Document` и ключей S3 |
| прерванный и возобновлённый перенос | возобновляемость, отсутствие дублей |
| запись формата 1 | отрабатывают существующие миграции `1 → 2` |
| запись новее приложения | отказ по правилу `NewerDataError`, данные не портятся |
| профиль с частично заполненными полями | корректное разделение на `OrganizationProfile` и `UserProfile` |
| профиль с неизвестными ключами | лишние ключи не попадают ни в один профиль и попадают в отчёт |
| два участника с разными персональными данными | персональные поля не смешиваются между пользователями |

## 9. Условия, при которых откат обязателен

| Триггер | Действие |
|---|---|
| Расхождение счётчиков источника и цели | остановка, откат на S3, повторный импорт |
| Любая потеря данных браузера | немедленная остановка всех этапов |
| Ошибка в доменной логике, проявившаяся на перенесённых данных | откат чтения (S4), разбор, исправление, повтор |
| Рост доли расхождений при dual-read выше согласованного порога | возврат к чтению из браузера |
| Любая неисправленная утечка данных между организациями | полная остановка, откат, разбор инцидента |
| Неуспешная проверка восстановления (S9) | production не считается готовым; блокирующий результат |
| Дубли платежей при повторной доставке вебхука | остановка биллинга флагом, разбор, ручная сверка |

## 10. Что делать нельзя

- Откатываться удалением данных браузера.
- Откатываться «вручную» правкой записей в БД.
- Переносить повторно поверх неисправленного кода без новой сверки.
- Считать перенос успешным без сходимости счётчиков и агрегатов.
- Удалять строки `AuditEvent` при откате.
- Удалять строки `Payment` при откате биллинга.
- Начинать этап до подтверждения предыдущего.
- Запускать вторую реплику `app` до завершения S8.

## 11. Обязательные меры безопасности переноса

| Мера | Причина |
|---|---|
| Экспорт снимается **до** любых изменений в приложении | иначе сравниваются разные моменты данных |
| Копия файла сохраняется **вне** репозитория и вне браузера | она содержит персональные данные и коммерческую тайну |
| Доступ к копии — только владельцу проекта | персональные данные |
| Копия имеет ограниченный срок хранения и удаляется после успешной подписи | принцип минимизации |
| Журнал переноса не содержит содержимого документов и реквизитов | только идентификаторы, счётчики, хеши |
| Перенос выполняется в фоне воркером pg-boss с возможностью остановки | операция долгая и должна быть прерваемой |

## 12. Что запрещено на этом этапе

- не запускать экспорт из браузера;
- не создавать и не выполнять миграции Prisma;
- не менять IndexedDB;
- не удалять браузерные данные;
- не менять существующие route handlers;
- не переводить ни одну существующую функцию на чтение из БД.
