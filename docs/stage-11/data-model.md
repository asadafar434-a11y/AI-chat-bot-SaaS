# Целевая модель данных: PostgreSQL + Prisma

**Статус: предложение.** Файл `prisma/schema.prisma` на этом этапе **не создан**, миграции **не созданы** и
**не запускались**, схема БД **не изменялась**. Ниже — контракт модели, который этап S1 реализует
аддитивной миграцией.

## 1. Принципы

1. **Аддитивность.** Первый этап только добавляет таблицы. Ни одного `DROP`, ни одного `ALTER` с потерей
   данных, ни одной необратимой миграции без процедуры отката.
2. **Сначала JSONB, потом нормализация.** Домен уже проверен и покрыт 508 тестами. Переписывать структуру
   `Purchase` в реляционные строки на первом этапе — это перенос 508 тестов на непроверенную схему.
   Поэтому тело закупки переносится как `JSONB` **без изменения формы**: ключи совпадают с текущим
   TypeScript-типом, и доменные функции продолжают работать без единой правки.
3. **Никаких выдуманных бизнес-правил.** Уникальность и обязательность вводятся только там, где правило
   уже известно из кода или из требований безопасности.
4. **Прозрачность происхождения.** У каждой перенесённой записи сохраняются `legacyId` и
   `originalFormatVersion`, поэтому импорт идемпотентен и откат возможен по первоисточнику.
5. **Tenant-скоупинг в схеме, а не в коде.** У каждой бизнес-таблицы есть `organizationId`; запрос без
   него на бизнес-таблицу запрещён на уровне репозитория.
6. **Разделение корпоративного и персонального.** Реквизиты организации и данные человека живут в разных
   таблицах и не смешиваются — см. §4.

### 3.2 User

Человек. Персональные данные и личные настройки — здесь, корпоративные реквизиты — в `OrganizationProfile`.

| Поле | Тип | Описание |
|---|---|---|

| `emailVerified` | `DateTime?` | |
| `name` | `String?` | отображаемое имя |
| `image` | `String?` | |
| `passwordHash` | `String?` | хеш; в клиент не отдаётся, в логи не попадает |
| `preferences` | `Json @default("{}")` | **личные настройки** пользователя |
| `createdAt` / `updatedAt` | `DateTime` | |

**Что входит в `preferences`** (личные настройки, переносимые между устройствами):

| Ключ | Назначение |
|---|---|
| `locale` | язык интерфейса |
| `timezone` | часовой пояс для показа сроков |
| `defaultView` | вид списка закупок по умолчанию |
| `aiConsentAt` | отметка о согласии на передачу данных во внешний ИИ |

**Что НЕ входит и остаётся локальным браузера** (настройки устройства, не личные настройки человека):
тема оформления, отметки прочитанного уведомлений, включён ли разбор сканов, согласие на передачу данных
за рубеж, состояние мастера заполнения. Это решение R11: такие значения не имеют смысла при смене
устройства и не являются настройками человека.

Уникальность `email` оправдана: без неё «один человек — один аккаунт» не выражается, а способ входа
построен на email.

### 3.6 Purchase

Тело закупки целиком сохраняется в `payload` без изменения формы. Источник истины — текущий тип
`Purchase` (`web/src/lib/purchase.ts:17-53`).

| Поле | Тип | Описание |
|---|---|---|
| `id` | `String @id @default(cuid())` | |
| `organizationId` | `String` | → `Organization`, индекс |
| `createdByUserId` | `String?` | → `User`; `null` для перенесённых из IndexedDB |
| `payload` | `Json` | поля `Purchase`, кроме `v`: `subject/short/files/requirements/criteria/tp/tpDraft/parts/check/chat/priceCalc/tpPrice/fieldValues/confirmed/submitReady/submitted/sample/sampleVersion/scans/docs/tpDocs/unreadable/createdAt` |
| `status` | `enum PurchaseStatus { draft submitted archived }` | соответствует сегодняшнему `submitted?: boolean` и разделам «В работе» / «Поданы» |
| `originalFormatVersion` | `Int` | значение `v` из IndexedDB, для трассировки |
| `legacyId` | `String?` | исходный `id` из IndexedDB; индекс; `null` для новых записей |
| `createdAt` / `updatedAt` | `DateTime` | |

Поля, которые **не** попадают в `payload`:
- тексты документов — уходят в S3 на этапе S6, в БД остаются только метаданные и ссылки (см. 3.7);
- `docs` и `tpDocs` (`DocStamp[]`) — остаются в `payload`, это отпечатки содержимого, а не тексты;
- `chat` (`ChatMessage[]`) — остаётся в `payload`; при росте объёма выносится отдельно, решение отложено.

Индексы: `@@index([organizationId, updatedAt])` для списка закупок, `@@index([organizationId, status])`
для фильтра, `@@index([legacyId])` для идемпотентности импорта. Уникальности на `legacyId` нет —
перенос повторяем, и коллизия должна разрешаться сверкой, а не падением.

| Поле | Тип | Описание |

| `storageKey` | `String?` | **непрозрачный** ключ объекта в S3; заполняется на этапе S6 |
| `textKey` | `String?` | ключ извлечённого текста в S3; заполняется на этапе S6 |

| `ocr` | `Boolean @default(false)` | соответствует существующей настройке сканирования |

Тексты в PostgreSQL **не хранятся**: извлечённый текст крупных документов достигает сотен тысяч знаков,
а чтение идёт целиком. Текст лежит в S3, в БД — метаданные. Это же открывает путь к полнотекстовому
поиску позже, без миграции больших данных.

Колонки `storageKey` и `textKey` создаются **nullable** уже на этапе S1: до подключения S3 (этап S6) они
остаются пустыми, и это не требует отдельной миграции.

`storageKey` формируется сервером: `org/{organizationId}/doc/{documentId}/{random}`. Ключ никогда не
приходит от клиента (см. [storage-jobs-payments.md](storage-jobs-payments.md) §1.3).

### 3.12–3.15 Таблицы Auth.js

`Account`, `Session`, `VerificationToken` — стандартная модель Auth.js, создаётся на этапе S2, поля не
проектируются здесь, чтобы не расходиться с Auth.js. Два требования поверх стандарта:

1. **`Session` обязательна** — решение D4: серверные сессии в БД, а не JWT, иначе отзыв доступа невозможен.
2. **`VerificationToken` хранит хеш токена**, а не сам токен, и используется для подтверждения email и

## 4. Модель профиля: корпоративное и персональное разделены

### 4.1 Правило

| Что | Где живёт | Почему |
|---|---|---|
| Наименование, ИНН, КПП, ОГРН, ОКВЭД, категория МСП, налоговая система, НДС, адреса, банк, БИК, расчётный счёт | `OrganizationProfile.fields` | это данные организации, они одинаковы для всех её участников и подставляются в анкету, декларацию, цену и договор |
| Руководитель, подписант, контактное лицо, телефон, контактный email | `UserProfile.fields` | это данные конкретного человека; у двух участников одной организации они различаются |
| Язык, часовой пояс, вид списка по умолчанию, отметка о согласии на ИИ | `User.preferences` | личные настройки человека, переносятся между устройствами |
| Тема, отметки уведомлений, разбор сканов, согласие на передачу за рубеж | **не переносится**, остаётся в браузере | настройки устройства, а не человека |

### 4.2 Что это меняет в продукте

Раньше реквизиты были «одним человеком в одном браузере». Теперь корпоративная часть общая для организации,
персональная — у каждого участника своя. Практическое следствие: документы заявки, которые подписывает
конкретный человек, используют `UserProfile` этого человека; реквизиты в анкете, декларации, цене и
договорах берутся из `OrganizationProfile`. **В техническое предложение реквизиты не попадают никогда** —
это правило уже зафиксировано в коде (`web/src/lib/profile.ts:1-2`) и сохраняется.

### 4.3 Как сохраняется доменный код

Домен оперирует одним объектом из 20 полей (`Profile`). Чтобы не трогать 508 тестов, backend **собирает
этот объект на сервере** из двух профилей и передаёт домену:

```
Profile (20 ключей) = { ...OrganizationProfile.fields (15), ...UserProfile.fields (5) }
```

Это единственная точка, где две таблицы встречаются. Она же — единственное место, где нужно проверить,
что при пересечении ключей не происходит молчаливая подмена: при совпадении ключа приоритет имеет
`OrganizationProfile`, а факт подмены пишется в лог как диагностика. Подробнее —
в [preserved-code.md](preserved-code.md) §3.

## 5. Соответствие текущим данным IndexedDB

Источник: `web/src/lib/db.ts:6-16` — три базы, пять хранилищ.

| IndexedDB | Хранилище | Ключ | Текущий тип | Целевые таблицы |
|---|---|---|---|---|
| `tender-lawyer` | `purchases` | `id` | `Purchase` + `v` | `Purchase` (`payload`) |
| `tender-lawyer` | `documents` | `id` закупки (без `keyPath`) | массив записей документов | `Document` (строки) |
| `tender-lawyer-me` | `settings["profile"]` | имя настройки (без `keyPath`) | `Profile`, 20 полей | `OrganizationProfile` (15) + `UserProfile` (5) |
| `tender-lawyer-me` | `settings["profile-meta"]` | | | `OrganizationProfile.version` + `UserProfile.version` |
| `tender-lawyer-me` | `samples` | `id` | `myDocument` (`kinds`, `about`, текст) | `Sample` |
| `tender-lawyer-evidence` | `facts` | `id` | `Fact` + `v` | `Fact` |

Ключевые наблюдения, влияющие на схему:

1. **Формат записи уже версионируется.** Каждая запись несёт `v`, а `data-format.ts:14-33` содержит
   миграции `1 → 2` для `purchase` и `myDocument`. При переносе `v` сохраняется в
   `originalFormatVersion` / `version`, а при импорте запись прогоняется через существующий `fromStore` и
   приводится к текущему формату **существующим кодом**, а не новой логикой.
2. **Тексты документов лежат отдельно от закупки** — отдельным хранилищем без `keyPath`. Это удачное
   разделение: оно прямо ложится на «метаданные в PG, содержимое в S3».
3. **Настройки — только реквизиты.** `backup-format.ts:23` уже отсекает всё, кроме `profile` и
   `profile-meta`: тема, согласие, отметки уведомлений остаются локальными и в сервер не переносятся.
4. **`documents` не имеет `keyPath`** — записи адресуются номером закупки. Импорт обязан воспроизвести
   эту адресацию либо разворачивать её в строки `Document` с явным `purchaseId`.
5. **Реквизиты при переносе требуют решения по принадлежности.** До переноса реквизитов владелец
   продукта назначает организацию-получателя: одна исходная установка переносится в одну организацию
   (решение фиксируется в `LegacyImportBatch`). Если в организации несколько участников, персональные
   пять полей достаются пользователю, который их заполнил, остальные — организации.

## 6. Что в схему сознательно НЕ попадает

| Не переносим | Почему |
|---|---|
| `settings`: тема, согласие на передачу за рубеж, отметки уведомлений, включён ли OCR | настройки устройства, не бизнес-данные; `backup-format.ts` их уже исключает |
| скомпилированный `/product` | артефакт сборки, в `.gitignore` |
| копия данных (`Backup`) как отдельная сущность | файл — внешний формат переноса, а не строка БД |

## 7. Изоляция арендаторов на уровне схемы

Правило: **каждый запрос к бизнес-таблице обязан включать `organizationId`.** Репозиторий — единственное
место, где строятся запросы, и он принимает `organizationId` параметром, а не опциональным аргументом.

| Таблица | Скоупинг |
|---|---|
| `Organization`, `OrganizationProfile` | по `id` / `organizationId` |
| `User`, `UserProfile` | **не** по `organizationId`: доступ идёт через `Membership` |
| `Membership` | по `organizationId` |
| `Purchase`, `Document`, `Fact`, `Sample`, `AuditEvent` | по `organizationId` |
| `Invitation` | по `organizationId`; анонимный доступ только к принятию приглашения |
| `Payment` | по `organizationId` |
| `Account`, `Session`, `VerificationToken` | только по `userId` текущей сессии |

Отдельно контролируются места, где сегодня scope отсутствует:

| Место | Риск | Контроль |
|---|---|---|
| `web/src/app/api/*` принимает `id` закупки в теле запроса | подмена чужого `id` | `organizationId` берётся только из серверной сессии, запись ищется по паре `(organizationId, id)` |
| `aiHeaders(purchaseId)` (`web/src/lib/purchase.ts:56`) — `id` приходит от клиента в заголовке `x-application-id` и используется для учёта бюджета ИИ | подмена значения снимает лимит или приписывает расход чужому | считать по `organizationId` из сессии; клиентский заголовок больше не является источником учёта (риск R2) |
| `wipe.ts` / `deleteDatabases()` — «удалить все мои данные» | на сервере стирание должно быть tenant-scoped и аудируемым | удаление по `(organizationId, userId)` с записью в `AuditEvent`; полное стирание организации — только `owner` |
| чат и разбор документов присылаются текстом в теле запроса | подмена содержимого | допускается и остаётся: сервер доверяет присланному тексту как вводу, но **не** как идентичности |

## 8. Ограничения PostgreSQL

- Версия: 16.
- Доступ приложения по локальному TCP, без публичного порта.
- Схемы: `public` — приложение, `pgboss` — очередь. Схемы не смешиваются.
- `search_path` для приложения: `public` явно.
- Расширения: только `pgcrypto` для хешей, если понадобится. Полнотекстовый индекс — не на этом этапе.
- Пул соединений ограничен; при 2 репликах `app` суммарный пул не превышает доступный в Postgres.
- Удаление пользователя — `deletedAt` (мягкое), а не `DELETE`: журнал аудита и ссылки на автора сохраняются.
