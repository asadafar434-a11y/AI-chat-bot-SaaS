# Аутентификация, роли и изоляция арендаторов

**Статус: контракт. Auth.js не реализован на этом этапе.** `web/src/proxy.ts`, `web/src/lib/access.ts` и
`web/src/app/api/login/route.ts` не изменялись, зависимости не добавлялись.

## 1. Текущее состояние (фиксируем как исходную точку)

| Аспект | Факт | Файл |
|---|---|---|
| Способ входа | один общий пароль из `ACCESS_PASSWORD` | `web/src/lib/access.ts:9` |
| Сессия | cookie `tl_access`, срок 180 дней | `web/src/lib/access.ts:4-5` |
| Проверка | вычисление токена из пароля и сравнение `sameToken` | `web/src/lib/access.ts:18-30` |
| Идентичность пользователя | **отсутствует**: пользователя нет, есть факт «пароль введён» | — |
| Роли и организации | **отсутствуют** | — |
| Где проверяется | proxy/middleware для страниц и API | `web/src/proxy.ts` |

Следствие: сегодня приложение однопользовательское по смыслу. Любой, кто знает пароль, видит все данные
этого браузера-экземпляра. Никакой tenant-изоляции нет, потому что нет понятия арендатора.

Это не баг, который надо срочно чинить, — это исходное состояние продукта. Оно меняется аддитивно.

## 2. Первоначальный способ входа: email + пароль

**Зафиксировано решение D13.** Это способ входа первого этапа; он не является «одним из вариантов».

| Свойство | Значение | Обоснование |
|---|---|---|
| Идентификатор | email (нормализованный в lowercase) | не требует отдельного поля и совпадает с идентификатором восстановления |
| Секрет | пароль, хранится только хеш | — |
| Регистрация | отсутствует; аккаунт создаётся только приглашением или созданием `owner` | открытая регистрация не нужна продукту и создаёт мусорные организации |
| Кто создаёт `owner` | первый `owner` создаётся при первичной настройке на этапе S2 | см. §3 |
| Кто приглашает `member` | только `owner` приглашает `member` | см. §4 |
| Альтернативный вход через внешнего провайдера | **не входит в Stage 11** | передача идентификатора внешнему провайдеру — обработка персональных данных, требует отдельной оценки; точка расширения сохранена |

Почему не «сначала общий пароль, потом разберёмся»: общий пароль не создаёт идентичности, а без
идентичности невозможны ни `Membership`, ни tenant-изоляция, ни аудит. Это делает его тупиковым
промежуточным состоянием.

## 3. Порядок появления: БД → Auth.js → авторизация

Auth.js с серверными сессиями **невозможно спроектировать в деталях до появления БД**. Решение D4
фиксирует хранение сессии в таблице `Session`, а Auth.js требует адаптер поверх ORM. Пока нет таблиц и
Prisma, нет точки, к которой привязывается проектирование.

Поэтому весь аутентификационный контур появляется **одним каскадом на этапе S2**, после того как S1
создал БД, и раньше не строится ни в каком виде.

| Шаг | Что появляется | Зависимость |
|---|---|---|
| 1 | `User` (с `email`, `passwordHash`, `preferences`), `Organization`, `Membership` | S1: Prisma уже есть |
| 2 | `Session`, `Account`, `VerificationToken` | шаг 1 |
| 3 | таблица `Invitation` | шаг 1 |
| 4 | адаптер Auth.js поверх Prisma (`PrismaAdapter`), режим `database` | шаги 2–3 |
| 5 | обработчики: вход, первичное создание `owner`, принятие приглашения, сброс пароля | шаг 4 |
| 6 | `requireSession` → `requireMembership` → `requireRole` → `withOrgScope` | шаг 5 |
| 7 | подключение проверок к маршрутам и proxy | шаг 6 |

Чего **не существует** как промежуточного состояния:

- JWT-сессии «на всякий случай» — решение D4 их исключает, а переход с них на БД-сессии ломает все
  активные сессии;
- сессий в памяти процесса или в файле — они не переживают перезапуск и не работают в двух репликах;
- тестового или обходного входа — он создаёт путь, который потом придётся искать и удалять;
- авторизации без `Membership` — `requireRole` без строки `Membership` не имеет смысла.

Подробная схема связки и её место в архитектуре — [architecture.md](architecture.md) §1.1.

## 4. Приглашение и установка пароля приглашённым

Пользователь без пароля не является пользователем: до первого входа у него нет `User.passwordHash`.
Поэтому вход через приглашение — не «регистрация с подтверждением», а **одноразовый setup-flow**.

```
owner в интерфейсе                         приглашённый
────────────────────                       ─────────────
создаёт Invitation                         открывает /invite/<token>
  token = случайное значение                → сервер: найти Invitation по tokenHash
  в БД хранится только tokenHash            → проверить: не истёк ли, не accepted ли
  задаёт email и роль                      → если User с таким email есть — приглашение
  срок действия задаётся явно                всё равно привязывается к его membership
                                              иначе — форма «придумайте пароль»
                                            → принять: создать User с passwordHash,
                                              UserProfile, Membership с ролью из Invitation,
                                              Invitation.acceptedAt = now
                                            → войти
```

| Правило | Значение |
|---|---|
| Токен | случайный, достаточной длины; в БД — **только хеш** |
| Одноразовость | `acceptedAt` выставляется в той же транзакции; повторное открытие ссылки отклоняется |
| Срок действия | задаётся явно, по умолчанию короткий; истёкшее приглашение отклоняется, а не продлевается молча |
| Отзыв | `owner` может удалить приглашение до принятия |
| Анонимный доступ | только операция «принять приглашение», только в пределах одной организации, только по одноразовому токену |
| Что видит анонимный посетитель | ни данных организации, ни списка участников, ни подтверждения существования email |
| Повторное приглашение | создаёт новое приглашение; уже принятое не восстанавливается |
| Ошибки | «ссылка недействительна» и «срок истёк» различаются только по существу, без раскрытия внутренних деталей |

## 5. Сброс пароля

| Шаг | Что происходит |
|---|---|
| 1 | Пользователь отправляет email на странице входа |
| 2 | Сервер **всегда** отвечает одинаково: «если такой аккаунт есть, отправили письмо». Это исключает перебор существующих email |
| 3 | Сервер создаёт `VerificationToken` с коротким сроком действия; в БД — **только хеш** |
| 4 | Письмо отправляется асинхронно через фоновое задание; ссылка ведёт на `/reset-password?token=…` |
| 5 | Пользователь задаёт новый пароль |
| 6 | Сервер проверяет хеш токена и срок, обновляет `passwordHash`, удаляет токен |
| 7 | **Все сессии этого пользователя удаляются** — смена пароля завершает старые сессии |
| 8 | Событие `auth.password_reset` пишется в `AuditEvent` |

Ограничение попыток на отправку письма — на том же счётчике в PostgreSQL, что и защита входа от перебора,
а не в памяти процесса (риск R1).

## 6. Двухфакторная аутентификация — точка расширения, не часть Stage 11

2FA **не входит** в Stage 11. Это осознанное ограничение объёма, а не упущение.

| Что | Статус |
|---|---|
| Подтверждение email при приглашении | обязательно уже в Stage 11: `Invitation` требует рабочий email |
| TOTP / аппликация | **вне Stage 11**; точка расширения — `User` и слой проверок входа |
| SMS / push | **вне Stage 11**; требует отдельного решения по обработке персональных данных |
| Аппаратные ключи | **вне Stage 11** |

Чтобы добавление 2FA позже не оказалось переписыванием:

1. проверка фактора входа изолирована в одном модуле, а не размазана по обработчикам;
2. решение «вход разрешён» принимается в одной точке и возвращает готовую идентичность — добавление
   второго фактора добавляет проверку, а не меняет её форму;
3. `Session` хранит факт аутентификации, а не способ её получения: добавление фактора не требует
   менять схему сессий;
4. UI-состояние «требуется второй фактор» — это состояние существующего потока входа, а не новый экран.

## 7. Целевая модель аутентификации

Auth.js (NextAuth v5) в режиме **серверных сессий в базе данных**, появляется на этапе S2.

| Решение | Обоснование |
|---|---|
| Database sessions, а не JWT | отзыв сессии должен быть немедленным; JWT нельзя отозвать без блок-листа. При переносе данных и разборе инцидентов JWT без блок-листа неприемлем |
| Стандартная модель Auth.js (`User` + `Account` + `Session` + `VerificationToken`) | не изобретаем аутентификацию; состав — [data-model.md](data-model.md) §2.3 |
| `passwordHash` в `User`, значение не отдаётся клиенту | хеш не логируется и не выбирается в запросах профиля |
| Сессия проверяется **на сервере** в каждом защищённом обработчике | клиентская метка входа не является доказательством |
| Персональные данные и личные настройки — в `User` | корпоративные реквизиты в `OrganizationProfile`; смешивание запрещено, см. [data-model.md](data-model.md) §4 |

## 8. Правило доверия

Запрещено принимать от клиента и использовать как идентичность:

- `role`;
- `organizationId`;
- `userId`;
- `purchaseId` как признак владения;
- `storageKey` документа;
- любые значения из тела запроса, определяющие, чьи данные читать или писать.

Разрешено принимать от клиента:

- идентификатор сущности **внутри уже установленной организации** — как вторичный ключ поиска, всегда в
  паре с `organizationId` из серверной сессии;
- содержимое файлов и тексты документов — как вход для разбора, но не как идентичность;
- значения полей бизнес-сущности — после валидации схемой.

Правило «кнопка скрыта» **не является** границей безопасности: проверка выполняется в сервисе, независимо
от того, что отрисовал интерфейс.

## 9. Контракт авторизации

Четыре функции, которые обязаны существовать до появления любой новой серверной точки доступа. Это
перечень API для этапа S2, не реализация.

| Функция | Что гарантирует | Отказ |
|---|---|---|
| `requireSession()` | есть аутентифицированный пользователь; возвращает `{ userId, sessionId }` | 401 |
| `requireMembership(orgId?)` | существует Membership пользователя; возвращает `{ organizationId, userId, role }` | 403 |
| `requireRole("owner")` | роль пользователя в текущей организации достаточна | 403 |
| `withOrgScope(query, organizationId)` | любой запрос к бизнес-таблице ограничен организацией | программная ошибка, если scope не передан |

Порядок проверок на каждом защищённом пути, без исключений и без «мелких» исключений:

1. аутентифицирован ли пользователь;
2. состоит ли он в организации;
3. достаточно ли его роли;
4. принадлежит ли целевая запись этой организации и этому пользователю.

Шаг 4 выполняется **в том же запросе**, что и чтение: `where: { id, organizationId }`. Проверка «сначала
прочитали, потом сравнили» недопустима — она создаёт окно и допускает утечку через различие ответов.

## 10. Роли

| Возможность | `owner` | `member` |
|---|---|---|
| Смотреть закупки, документы, факты своей организации | да | да |
| Создавать и изменять закупки, загружать документы | да | да |
| Скачивать документы организации | да | да |
| Приглашать и удалять участников | да | нет |
| Менять роль участника | да | нет |
| Удалить организацию | да | нет |
| Смотреть аудит и расходы ИИ | да | нет |
| Сменить тариф / инициировать оплату | да | нет |
| Экспортировать данные организации | да | нет |

Инварианты:

- в организации всегда есть хотя бы один `owner`;
- последнего `owner` нельзя понизить или удалить;
- понижение и удаление инициирует `owner`; понизить себя нельзя, если это последний owner;
- обе операции пишутся в `AuditEvent`;
- роль `member` **не может** быть источником доступа к данным другой организации ни при каких условиях;
- `member` не может создавать приглашения, даже если получит ссылку в интерфейсе: проверка в сервисе.

## 11. Переходный период

Существующий вход по общему паролю сохраняется рабочим, пока идёт перенос данных. Это осознанное
решение: иначе перенесённые данные окажутся у пользователя без доступа к ним.

| Этап | Состояние входа | Состояние данных |
|---|---|---|
| A | `ACCESS_PASSWORD` + `tl_access` (как сейчас) | IndexedDB |
| B | `ACCESS_PASSWORD` работает **или** Auth.js; флаг выбора | IndexedDB + чтение с сервера за флагом |
| C | только Auth.js | серверные данные |
| D | только Auth.js | только серверные данные, IndexedDB read-only |

Этапы A–D лежат **внутри** этапов S2–S5 и не отдельны от них: переходный период — часть миграции, а не
параллельный трек.

`web/scripts/check-host.mjs` использует `ACCESS_PASSWORD` и cookie `tl_access` для своей проверки. Значит,
на этапах A–C переменная `ACCESS_PASSWORD` и её обработка **обязаны оставаться рабочими**, иначе сломается
существующая проверка сборки. После этапа D скрипт обновляется отдельной задачей (риск R7).

## 12. Защита входа и сессии

| Требование | Решение |
|---|---|
| Ограничение попыток входа | счётчик переносится из памяти процесса в PostgreSQL; сегодня лимит живёт в `Map` (`web/src/lib/rate-limit.ts:40`) и при двух репликах удваивается |
| Одинаковый ответ при ошибке входа | одинаковый текст для неверного пароля и для несуществующего пользователя |
| Cookie сессии | `httpOnly`, `sameSite=lax`, `secure` в production |
| CSRF | встроенная защита Auth.js; для собственных `POST`-обработчиков — проверка origin |
| Отзыв сессии | удаление строки сессии; принудительный выход всех устройств — смена `updatedAt` пользователя |
| Утечка хеша | `passwordHash` не выбирается в запросах профиля, не логируется, не возвращается в API |
| Публичные страницы | `/privacy`, `/terms`, `/contacts`, `/login`, `/tariffs`, `/consent`, `/consent-transfer` — без сессии, как сейчас |
| Ошибка аутентификации | одинаковый текст для неверного пароля и для несуществующего пользователя |

## 13. Персональные данные

- Персональные данные сегодня лежат в реквизитах (`Profile.phone`, `Profile.email`, `Profile.head`,
  `Profile.contactPerson`), в фактах базы доказательств (ФИО сотрудников в `fields`) и в переписке с ИИ
  (`Purchase.chat`).
- После переноса они **разделены**: корпоративные реквизиты организации — в `OrganizationProfile`,
  персональные данные и личные настройки человека — в `UserProfile` и `User.preferences`. Подробно —
  [data-model.md](data-model.md) §4.
- Весь этот класс данных после переноса хранится в РФ и попадает в `AuditEvent` **только** как
  идентификаторы.
- Метрики и логи не включают содержимое документов, реквизиты и тела запросов к ИИ — см.
  [operations.md](operations.md) §2.2.
- Выбор способа входа через внешнего провайдера — **вне Stage 11**: передача идентификатора внешнему
  провайдеру является обработкой персональных данных и требует отдельной оценки до реализации.

## 14. Что запрещено на этом этапе

- не реализовывать Auth.js и не проектировать его поток сессий в деталях до появления БД и адаптера;
- не создавать таблицы сессий, `User`, `Invitation` и не добавлять миграции под них;
- не менять `web/src/proxy.ts`, `web/src/lib/access.ts`, `web/src/app/api/login/route.ts`;
- не добавлять зависимости Auth.js в `web/package.json`;
- не выдавать тестовые или обходные пути аутентификации;
- не вводить открытую регистрацию: аккаунт создаётся только приглашением или первичным созданием `owner`;
- не считать UI-скрытие кнопки проверкой доступа;
- не реализовывать 2FA — это точка расширения (§6).
