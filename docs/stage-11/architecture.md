# Границы слоёв и топология

## 1. Зафиксированные границы

Приложение остаётся **монолитом** (Next.js App Router) с явным внутренним разделением на четыре слоя.
Дробление на отдельные сервисы не планируется: объём команды и трафик этого не оправдывают, а микросервисы
добавили бы сетевую сложность без выигрыша в надёжности.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. FRONTEND — web/src/app/**, web/src/components/**                         │
│    React-компоненты, страницы, клиентские island-обёртки.                    │
│    Правило: не содержит прямых обращений к БД, к S3 и к платёжному провайдеру.│
│    Правило: не принимает решение о доступе — только прячет кнопки.            │
└───────────────────────────────┬─────────────────────────────────────────────┘
                                │ только HTTP: route handler / server action
┌───────────────────────────────▼─────────────────────────────────────────────┐
│ 2. BACKEND — web/src/app/api/**, web/src/server/** (новый слой)             │
│    Аутентификация, авторизация, валидация входа, HTTP-контракты,             │
│    rate limit, метрики ИИ, подпись download-URL.                            │
│    Правило: не содержит доменных правил. Не знает про 44-ФЗ/223-ФЗ.         │

┌───────────────────────────────▼─────────────────────────────────────────────┐
│ 3. DOMAIN — существующий web/src/lib/** (сохраняется)                       │
│    75 «чистых» модулей: разбор закупок, ТП, критерии, цены, сроки,           │
│    реквизиты, поиск по документам, генерация DOCX/PDF/ODT/ZIP.               │
│    Правило: детерминирован, без обращений к БД, сети, времени и случайности.│
│    Правило: тесты web/src/lib/*.test.ts (508 шт.) обязаны остаться зелёными. │
└───────────────┬───────────────────────────────────┬─────────────────────────┘

┌───────────────▼──────────────────┐  ┌─────────────▼───────────────────────────┐
│ 4a. PERSISTENCE — Prisma          │  │ 4b. OBJECT STORAGE — StorageAdapter     │
│     PostgreSQL, РФ                 │  │     S3-compatible, РФ                    │

                │                                    │
        ┌───────▼────────┐              ┌────────────▼────────────┐
        │ pg-boss (этап S8)│             │ ЮKassa (будущее, этап S10) │
```

### 1.1 Обязательная связка инфраструктуры: БД → Auth.js → авторизация

Три компонента появляются **строго последовательно, одним каскадом на этапе S2** и раньше не строятся:

```
этап S1                    этап S2 (одним изменением)          после S2
──────────────────────     ─────────────────────────────────     ────────────
PostgreSQL + Prisma   →   Session / Account / VerificationToken  →   requireSession()
                        +   таблица User + passwordHash             requireMembership()
                        +   Auth.js adapter поверх Prisma          requireRole()
                        +   /api/auth, /api/invitation, /api/...    withOrgScope()
```

Правила:

1. **Database sessions требуют БД.** Решение D4 фиксирует хранение сессии в таблице `Session`, а Auth.js
   требует адаптер поверх ORM. Пока нет этапа S1, нет ни таблицы сессий, ни Prisma, ни адаптера, и полный
   поток сессий **не проектируется в деталях** — это был бы проект без основания.
2. **Авторизация не проектируется без Auth.js.** `requireMembership`, `requireRole` и `withOrgScope`
   работают с `userId` и `Membership`. Идентичность пользователя появляется только вместе с `Session`.
   Поэтому функции из [auth-tenancy.md](auth-tenancy.md) §4 — это контракт следующего этапа, а не
   предварительно написанный код.
3. **Промежуточного состояния «Auth.js без БД» не существует.** Ни JWT-варианта, ни in-memory сессий, ни
   тестового обхода: любой из них создал бы схему, которую придётся переделывать.
4. Порядок внутри этапа S2: `User` + `Membership` → `Session`/`Account`/`VerificationToken` → Auth.js
   adapter → обработчики входа → `Invitation` → функции авторизации → подключение защиты к маршрутам.
5. Единственное, что появляется **до** S1, — это привычка не принимать `role`, `organizationId` и `userId`
   от клиента. Она соблюдается уже сейчас и не требует БД.

## 2. Правило зависимостей

Разрешено: `Frontend → Backend → Domain → {Persistence, ObjectStorage, JobQueue, PaymentProvider}`.

Запрещено:

- `Domain → любой инфраструктурный модуль`. Доменный код не знает про Prisma, S3, pg-boss, YooKassa и HTTP.
  Инфраструктура внедряется в сервисы слоя 3 через адаптеры.
- `Frontend → Persistence/ObjectStorage/Payment` напрямую.
- `Persistence → Backend` и любые обратные стрелки.
- Импорт доменного кода в React-компоненты с побочными эффектами: компонент может импортировать чистую
  функцию домена, но не хранилище.

Проверка правила автоматизируется линтером на следующем этапе (import-boundary правило в
`web/eslint.config.mjs`); на этом этапе правило зафиксировано документально.

## 3. Что считается «серверной» границей

Граница проходит по `web/src/proxy.ts` (Next.js proxy/middleware) и по `web/src/app/api/**/route.ts`.

Сейчас 14 route handler, **все — `POST`**, все уже требуют пароль:

| Route | Назначение | Состояние |
|---|---|---|
| `/api/login` | вход по общему паролю, выдаёт `tl_access` | будет заменён Auth.js с переходным периодом |
| `/api/chat` | чат с ИИ по закупке | не меняется на этом этапе |
| `/api/check` | проверка заявки перед подачей | не меняется |
| `/api/documents` | разбор и чтение документов (OCR опционален) | не меняется |
| `/api/requirements` | разбор требований заказчика | не меняется |
| `/api/my-docs/facts` | запись фактов базы доказательств | не меняется |
| `/api/my-docs/profile` | извлечение реквизитов из документов | не меняется |
| `/api/my-docs/sort` | сортировка образцов участника | не меняется |
| `/api/tp` | техническое предложение | не меняется |
| `/api/tp/part`, `/api/tp/docx`, `/api/tp/odt`, `/api/tp/pdf`, `/api/tp/zip` | сборка частей и файлов заявки | не меняется |

**Ограничение этапа: эти обработчики не меняются.** Ни один из них сегодня не читает и не пишет IndexedDB:
браузер присылает нужные данные в теле запроса. Это позволяет менять источник хранения, не трогая
HTTP-контракты, — сначала добавляются новые, старые остаются и переключаются флагом.

## 4. Существующие серверные примитивы и их потолок

| Примитив | Файл | Хранилище состояния | Потолок |
|---|---|---|---|
| Пароль доступа | `web/src/lib/access.ts` | `process.env.ACCESS_PASSWORD`, cookie `tl_access` на 180 дней, сравнение `sameToken` | один общий пароль на всё приложение; **пользователей нет** |
| Rate limit | `web/src/lib/rate-limit.ts:40` | `Map` внутри `createLimiter` | **на процесс**: при двух репликах лимит удваивается |
| Бюджет ИИ | `web/src/lib/ai-meter.ts:17` | `Map` в памяти процесса | **на процесс**: счёт расходов теряется при рестарте и не суммируется между репликами |
| Дедупликация запросов ИИ | `web/src/lib/ai-meter.ts:41` | `Map` промисов в памяти | **на процесс** |
| Глобальный бюджет | `web/src/lib/ai-guard.ts:13` | синглтон модуля | **на процесс** |
| IP клиента | `web/src/lib/rate-limit.ts:71` | последний элемент `X-Forwarded-For` | корректно только за доверенным обратным прокси |

Вывод: **до горизонтального масштабирования эти примитивы обязаны переехать в PostgreSQL.** Это не
оптимизация, а условие корректности. Планируется в [operations.md](operations.md) и
[decisions-and-risks.md](decisions-and-risks.md) (риск R1).

## 5. Топология развёртывания в РФ

Один Docker-образ Next.js (standalone), один процесс-воркер pg-boss, внешние сервисы в РФ.

```
                    Интернет (HTTPS, 443)
                             │
                    ┌────────▼────────┐
                    │  nginx / Caddy  │  TLS-терминация, security headers,
                    │  в РФ, 1 VM     │  client_max_body_size 45 МБ,
                    └────────┬────────┘  rate limit на границе
                             │ http, приватная сеть
        ┌────────────────────┴────────────────────┐
        │                                         │
┌───────▼────────┐                       ┌────────▼────────┐
│ app            │                       │ worker          │
│ next start     │                       │ pg-boss +       │
│ (standalone)   │                       │ скрипты миграции│
│ 2 реплики      │                       │ 1 реплика       │
│ не раньше S8   │                       │ с этапа S8      │
└───────┬────────┘                       └────────┬────────┘
        │                                          │
        ├──────────────┬───────────────┬───────────┤
        │              │               │           │
┌───────▼──────┐ ┌─────▼──────┐ ┌──────▼───────┐ ┌─▼──────────────┐
│ PostgreSQL   │ │ pg-boss    │ │ S3-compatible│ │ ЮKassa (будущее)│
│ 16, в РФ     │ │ та же БД   │ │ бакет, в РФ  │ │ api ЮKassa     │
│ без публичн. │ │ отдельная  │ │ приватный    │ │ исходящие      │
│ доступа      │ │ схема      │ │ бакет,       │ │ только к       │
└──────────────┘ └────────────┘ └──────────────┘ └────────────────┘
        │
┌───────▼──────────────────────────────┐
│ Стороннее хранилище бэкапов, в РФ    │
│ (регулярные PITR-бэкапы)             │
└──────────────────────────────────────┘
```

Ограничения сети: приложение, worker, PostgreSQL и S3 — в одной приватной сети РФ; наружу открыт только
443 на прокси; SSH по ключу, парольный вход отключён; доступ к БД из интернета закрыт.

## 6. Модель процессов

| Процесс | Роль | Реплики | С какого этапа |
|---|---|---|---|
| `app` | HTTP: страницы, route handlers, SSR | 1 | S1 |
| `app` | то же | 2 | **только после S8**, когда лимиты и бюджеты в БД |
| `worker` | pg-boss: фоновая обработка, перенос данных, планировщики | 1 (pg-boss сам обеспечивает блокировку задач) | S8 |
| `postgres` | БД приложения | 1 основной + бэкапы | S1 |
| `s3` | объектное хранилище документов | управляемое | S6 |

Критично: **rate limit и бюджет ИИ переходят в PostgreSQL до появления второй реплики `app`.** До этого
момента допустима одна реплика — иначе лимиты перестанут работать. Это жёсткое ограничение на этапы S1–S7.

Обязательная последовательность этапов S0–S11 и их границы описаны в [README.md](README.md). Здесь —

Состав таблиц приведён в [data-model.md](data-model.md) §2 и **не дублируется** в этом документе.

## 8. Ограничения инфраструктуры, зафиксированные контрактом

1. Никаких данных персональных и коммерческих пользователей за пределами РФ.
2. Наблюдаемость в production настраивается так, чтобы персональные данные не передавались в
   сторонние сервисы без необходимости. Допустимы два варианта: self-hosted мониторинг в РФ либо
   аккуратно настроенный внешний сервис — и второй вариант требует отдельной legal/privacy оценки
   до подключения, а не после. Подробно — [operations.md](operations.md) §2.4, решение D9.
3. Секреты только через переменные окружения/Docker secrets, `.env.example` — с плейсхолдерами.
4. Никогда не хранить сырые данные карт; секреты ЮKassa — только на сервере.
5. Ключ `ANTHROPIC_API_KEY` — серверная переменная, в клиентский бандл не попадает.
