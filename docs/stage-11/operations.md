# Эксплуатация: резервные копии, восстановление, наблюдаемость, Docker

**Статус: контракт.** Dockerfile, дашборды и процедуры не создавались на этом этапе.

## 1. Резервные копии и восстановление

### 1.1 Что резервируется

| Актив | Метод | Частота | Почему |
|---|---|---|---|
| PostgreSQL, включая схему `pgboss` | непрерывный WAL-архив (PITR) + ежедневная полная копия | непрерывно + раз в сутки | даёт восстановление на произвольный момент; очередь задач лежит в той же БД и копируется вместе с ней |
| Объекты S3 | включённое версионирование бакета + регламентное копирование в отдельный бакет | по версии, регламент согласуется | версионирование защищает от перезаписи |
| Конфигурация | репозиторий Git (compose, Dockerfile, миграции, `.env.example`) | на каждый коммит | воспроизводимость развёртывания |
| Схема и миграции | Prisma-миграции в Git | на каждый коммит | повторяемость сборки схемы |

Копии хранятся **в РФ**, отдельно от основного хранилища, с ограниченным доступом. Копия PostgreSQL и копия
бакета лежат в разных сервисах: потеря одного не должна означать потерю обоих.

### 1.2 Цели восстановления

Значения требуют утверждения владельцем; ниже — предлагаемые значения, на которых строится процедура.

| Показатель | Предлагаемое значение | Смысл |
|---|---|---|
| RPO | не более 15 минут | при потере сервера теряется не более четверти часа работы |
| RTO | не более 4 часов | приложение возвращается в тот же день |
| Глубина хранения | 30 дней | покрывает расследование инцидентов |

### 1.3 Обязательное условие: проверка восстановления

Резервная копия считается существующей **только после успешного восстановления**. Процедура проверки:

1. Развернуть отдельный экземпляр БД из последней полной копии.
2. Догнать его до текущего момента WAL-архивом.
3. Поднять приложение против этой БД (тестовый контур, продакшен не затрагивается).
4. Прогнать `npm test` и `npm run check:host`.
5. Сверить контрольные счётчики с последним отчётом о переносе.
6. Зафиксировать дату и результат проверки.

Проверка выполняется **по расписанию** и результат фиксируется письменно. Непроверенная копия в
эксплуатационном смысле не существует.

### 1.4 Восстановление отдельных данных

Для точечного возврата (например, одного удалённого документа) полная выгрузка БД не применяется.
Используется точечное восстановление: чтение нужной версии объекта из бакета по версионированию плюс
восстановление строки из WAL/бэкапа. Порядок операций:

1. определить организацию и объект;
2. восстановить версию объекта в отдельный ключ, **не перезаписывая** текущий;
3. записать в `AuditEvent` событие восстановления;
4. подтвердить результат пользователем.

## 2. Наблюдаемость

### 2.1 Логи

Структурированные JSON-строки в stdout, собираются инфраструктурой. Формат фиксирован:

| Поле | Обязательность | Пример |
|---|---|---|
| `timestamp` | всегда | `2026-10-02T11:14:07.123Z` |
| `level` | всегда | `info` \| `warn` \| `error` |
| `event` | всегда | `ai.request`, `auth.login`, `document.download` |
| `requestId` | всегда | сквозной идентификатор запроса |
| `durationMs` | для операций с длительностью | `1284` |
| `status` | для HTTP | `200` |
| `organizationId` | когда безопасно | `org_…` |
| `userId` | когда безопасно | `usr_…` |

### 2.2 Что в логи попадать не может

| Запрещено | Почему |
|---|---|
| пароли и хеши паролей | утечка учётных данных |
| токены сессий и access-токены | утечка учётных данных |
| ключ `ANTHROPIC_API_KEY` | секрет внешнего сервиса |
| секреты ЮKassa | секрет платёжного провайдера |
| содержимое документов и тексты | персональные данные и коммерческая тайна |
| корпоративные реквизиты организации (`OrganizationProfile.fields`: ИНН, КПП, адреса, банк, расчётный счёт) | персональные данные и коммерческая тайна |
| персональные данные пользователя (`UserProfile.fields`: ФИО, телефон, контактный email) и личные настройки (`User.preferences`) | персональные данные |
| подписанные ссылки на объекты S3 | действующие временные учётные данные доступа |
| тела запросов к ИИ и ответы модели | персональные данные, частая и нечувствительная практика логировать всё подряд |
| полные имена файлов документов | могут содержать персональные данные |

IP-адрес, если он нужен для расследования, логируется в виде хеша. Идентификаторы документа и закупки
логируются как идентификаторы, а не как содержимое.

### 2.3 Метрики

| Метрика | Тип | Зачем |
|---|---|---|
| `http_requests_total{route,status}` | счётчик | доступность и распределение нагрузки |
| `http_duration_ms{route}` | гистограмма | медленные маршруты |
| `ai_requests_total{label,status}` | счётчик | использование ИИ |
| `ai_spend_rub{organizationId}` | счётчик | контроль бюджета |
| `ai_budget_exceeded_total` | счётчик | срабатывание лимита |
| `auth_login_total{result}` | счётчик | успехи, отказы, атаки |
| `rate_limit_rejected_total{window}` | счётчик | срабатывание лимитов |
| `job_completed_total{queue,status}` | счётчик | фоновые задачи |
| `migration_progress{entity,batch}` | gauge | прогресс переноса |

Метрики с `organizationId` в метке ограничены по мощности: при большом числе организаций метка
агрегируется, а детальные данные остаются в `AuditEvent`.

### 2.4 Наблюдаемость в production и передача данных третьим сторонам

**Требование (D9).** Наблюдаемость в production настраивается так, чтобы персональные данные **не передавались
в сторонние сервисы без необходимости**. Это требование о минимизации данных, а не запрет внешних сервисов.

Допустимы два варианта, и выбор между ними — решение владельца:

| Вариант | Что это значит | Когда выбирается |
|---|---|---|
| **A. Self-hosted мониторинг в РФ** | логи, метрики и ошибки собираются и хранятся на инфраструктуре в РФ; наружу ничего не уходит | вариант по умолчанию, если нет иного |
| **B. Внешний сервис, аккуратно настроенный** | сервис подключается **только после отдельной legal/privacy оценки**, которая фиксируется письменно до подключения: какие именно поля покидают РФ, куда, на каком основании и как долго хранятся | когда вариант A технически недостаточен |

Что бы ни было выбрано, обязательно:

1. Правила редактирования определены **до** подключения, а не после первого инцидента.
2. Из ошибки вырезаются тела запросов, заголовки авторизации, содержимое файлов и сами подписанные ссылки.
3. Передаются только стек, `requestId`, `event`, код статуса и, при необходимости, `organizationId`/`userId`.
4. Отключение передачи включается одной переменной окружения, и оно работает без перезапуска инфраструктуры.
5. Наличие и результат оценки фиксируются в журнале решений, а не в переписке.

Формулировка «152-ФЗ запрещает внешний мониторинг» в этом документе **намеренно не используется**: оценка
применимости требований к конкретной конфигурации — задача юридической функции, а не вывод из
архитектурного документа. Требование, которое здесь зафиксировано, — минимизация: не передавать то, без чего
работа невозможна.

### 2.5 Оповещения

| Событие | Порог |
|---|---|
| ошибки 5xx | больше 1% запросов за 5 минут |
| недоступность БД | немедленно |
| очередь pg-boss: задачи не берутся | длиннее обычного цикла |
| превышение бюджета ИИ | сразу при срабатывании лимита |
| неуспешное восстановление из копии | немедленно |
| истечение срока действия факта-доказательства | информационно, для владельца |

## 3. Docker-развёртывание

### 3.1 Образы

| Образ | Содержимое | Команда запуска |
|---|---|---|
| `app` | Next.js в режиме standalone | `node server.js` |
| `worker` | тот же код, вход в pg-boss | `node worker.js` |

Оба образа — из одного Dockerfile с разным `CMD`. Сборка воспроизводима: базовый образ закреплён по
конкретному тегу или по дате, зависимости ставятся по lockfile, `npm ci` не `npm install`.

### 3.2 Правила образа

| Правило | Следствие |
|---|---|
| multi-stage | в финальный образ не попадают исходники и dev-зависимости |
| non-root пользователь | процесс приложения не root |
| только `standalone`-трассировка Next.js | образ минимален |
| healthcheck | `GET /api/check`, без внешних зависимостей |
| никаких секретов в образе | секреты приходят только через окружение/Docker secrets |

### 3.3 Порядок развёртывания

1. Прогон `npm test`, `npm run build:host`, `npm run check:host` — в CI.
2. Сборка образов с тегом, соответствующим коммиту.
3. Резервная копия БД **до** миграции.
4. Применение аддитивной миграции Prisma.
5. Перезапуск `worker`, затем `app`.
6. Проверка `check:host` против развёрнутого экземпляра.
7. Наблюдение за ошибками 5xx и очередью.

Миграции применяются отдельным шагом и только аддитивные. Шаг 4 не входит в шаг 5: сначала схема, потом
код.

### 3.4 Конфигурация окружения

| Переменная | Обязательна в production | Примечание |
|---|---|---|
| `DATABASE_URL` | да | с этапа S1 |
| `AUTH_SECRET` | да | с этапа S2; до S2 не требуется |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_REGION` | да | с этапа S6 |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | да | через Docker secrets |
| `PGBOSS_DATABASE_URL` | да | с этапа S8 |
| `ANTHROPIC_API_KEY` | да | |
| `NODE_ENV` | да | `production` |
| `ACCESS_PASSWORD` | переходный период A–C | снимается после этапа D |
| `YOOKASSA_*` | нет | только после этапа S10 |

Обязательные переменные проверяются при старте: процесс, которому не хватает секрета, **не поднимается**
с понятной ошибкой, а не падает позже на первом запросе.
