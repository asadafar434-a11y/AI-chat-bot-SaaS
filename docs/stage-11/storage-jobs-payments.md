# Хранилище объектов, фоновые задачи, платежи

**Статус: контракт.** Зависимости не установлены, код не написан, S3 и pg-boss не подключены.

## 1. S3-compatible объектное хранилище в РФ

### 1.1 Зачем отдельное хранилище

Тексты документов после разбора — это сотни тысяч знаков на файл. Хранение таких объёмов в PostgreSQL
раздувает бэкапы, замедляет `VACUUM` и делает чтение «закупки целиком» дорогиой. Сейчас тексты лежат в
IndexedDB отдельным хранилищем без `keyPath` (`web/src/lib/db.ts:9`) — то есть разделение «закупка» /
«документы» уже существует и прямо ложится на разделение «метаданные в PG, содержимое в S3».

| Что | Где | Почему |
|---|---|---|
| Исходный файл (docx, xlsx, pdf, фото) | S3 | бинарные данные, нужны для повторного разбора |
| Извлечённый текст документа | S3 | крупные объёмы, чтение целиком |
| Метаданные (имя, размер, хеш, страницы, ключ) | PostgreSQL `Document` | нужны для списков, поиска, проверок |
| Разметка страниц, карта таблиц | S3, рядом с текстом | производная от текста, при пересчёте меняется целиком |
| Факты, реквизиты, параметры закупки | PostgreSQL | структурированные, небольшие, участвуют в проверках |

### 1.2 Требования к провайдеру

| Требование | Обоснование | Обязательность |
|---|---|---|
| Размещение в РФ | требование к персональным и коммерческим данным | обязательно |
| S3-совместимый API | стандарт, смена провайдера не должна быть переписыванием | обязательно |
| Отдельный **приватный** бакет | публичные ссылки на документы недопустимы | обязательно |
| Запрет публичного доступа на уровне бакета (private ACL + bucket policy, deny для `public-read`) | публичность не должна получаться по умолчанию или по недосмотру | обязательно |
| **Шифрование в покое (at rest), если провайдер его поддерживает** | SSE на стороне провайдера; при отсутствии поддержки — решение фиксируется отдельно, с компенсацией на уровне приложения | обязательно при наличии поддержки |
| Шифрование в транзите (HTTPS/TLS) | канал между приложением и хранилищем | обязательно |
| Версионирование объектов | защита от записи поверх существующего ключа | обязательно |
| Presigned URL с коротким сроком действия | выдача разовой ссылки вместо постоянного доступа | обязательно |
| Возможность снять доступ с бакета целиком | компрометация ключа → отзыв без правки кода | обязательно |
| Отдельные учётные данные для приложения | доступ приложения не должен совпадать с доступом администратора | желательно |

Шифрование в покое формулируется как «где провайдер поддерживает» сознательно: S3-совместимые
провайдеры в РФ различаются по этому пункту, и объявлять поддержку, которой нет, нельзя. Если выбранный
провайдер не поддерживает SSE на стороне сервиса, это фиксируется как отдельное решение с указанием
компенсирующей меры (клиентское шифрование содержимого перед `putObject` или размещение в бакете с
гарантированным шифрованием), а не молча пропускается.

Конкретный провайдер (Yandex Object Storage, Selectel, Cloud.ru и другие) выбирает владелец. Код обязан
опираться на интерфейс, а не на SDK конкретного поставщика.

### 1.3 Ключи объектов

Формат ключа: `org/{organizationId}/doc/{documentId}/{random}`, где `random}` — серверная случайность
не менее 128 бит.

| Свойство | Как обеспечивается |
|---|---|
| Непрозрачность | имя файла пользователя в ключ **не входит**; ключ не даёт подсказки о содержимом |
| Организационный скоупинг | `organizationId` — первый сегмент; объект одной организации физически отделён от другой |
| Однозначность | `documentId` исключает коллизию, случайный суффикс исключает перечисление |
| Проверка владения | по ключу определяется `organizationId`, затем сверяется, что строка `Document` с таким `storageKey` принадлежит тому же `(organizationId, documentId)` |
| Ключ от клиента | **не принимается ни в одном виде**; клиент не может указать ни организацию, ни имя файла, ни ключ |

Правило: клиентский `storageKey` отвергается на границе валидации, а не используется. Ключ строит сервер
из `documentId`, который сам был выдан сервером.

### 1.4 Контракт `StorageAdapter`

Граница, через которую backend обращается к хранилищу. Определение — для этапа S6.

| Операция | Контракт |
|---|---|
| `putObject(key, body, contentType)` | возвращает `{ key, etag }`; перезапись по тому же ключу запрещена |
| `getObject(key)` | возвращает содержимое; отсутствующий ключ — доменная ошибка «нет такого документа» |
| `headObject(key)` | метаданные без загрузки тела |
| `deleteObject(key)` | удаление; вызывается только из сервиса с аудитом |
| `createSignedUrl(key, { expiresIn })` | возвращает `{ url }`; срок жизни — **короткий**, единицы минут |
| `deletePrefix(prefix)` | только для отзыва всех объектов организации |

Правила, обязательные для реализации:

1. Ключ формирует **сервер** по схеме из §1.3. Ключ никогда не приходит от клиента и не выводится из
   имени файла.
2. Постоянных публичных URL нет: ни у объекта, ни у бакета. Формат постоянной ссылки не используется в
   коде вообще.
3. `createSignedUrl` **не является** точкой авторизации и не вызывается напрямую из обработчика. Сначала
   выполняется проверка доступа, затем выдаётся ссылка — см. §1.5.
4. Логи операций хранилища не содержат содержимого объектов, полных имён файлов и самих подписанных
   ссылок: фиксируются `organizationId`, `documentId`, операция, результат и байты.

### 1.5 Авторизация перед каждым скачиванием

Порядок обязателен и не переставляется:

```
1. Аутентификация          серверная сессия (этап S2)
2. Membership              пользователь состоит в организации документа
3. Владение записью        Document принадлежит этой организации
4. Проверка роли           роль допускает скачивание
5. Только теперь выдача    короткоживущий presigned URL  (или поток через
                           аутентифицированную точку — вариант по умолчанию)
6. Аудит                   document.downloaded в AuditEvent (этап S7)
```

| Требование | Решение |
|---|---|
| Авторизация перед каждым скачиванием | шаги 1–4 выполняются **до** шага 5, в том же запросе; подпись выдаётся только после успешной проверки |
| Проверка «прочитал — потом сравнил» | недопустима: сверка выполняется в условии выборки, а не после |
| Короткоживущая ссылка | срок из `S3_SIGNED_URL_TTL_SECONDS`, по умолчанию единицы минут; значение фиксируется явно, а не «на усмотрение провайдера» |
| Ссылка не кэшируется | `Cache-Control: no-store` на ответе со ссылкой; сама ссылка не пишется в логи и в `AuditEvent` |
| Отсутствующий документ и чужой документ | одинаковый ответ, чтобы по различию нельзя было определить существование чужого объекта |
| По умолчанию | аутентифицированная точка скачивания, а не выдача ссылки: так проверка доступа гарантированно выполняется на каждом запросе |

### 1.6 Контрольный список требований к S3

Соответствие проверяется до этапа S6; каждый пункт — проверяемое утверждение, а не намерение.

| # | Требование | Где зафиксировано | Как проверяется |
|---|---|---|---|
| 1 | Бакет приватный | §1.2 | `GetPublicAccessBlock`/политика бакета: публичный доступ запрещён; `ListBuckets` не показывает бакет наружу |
| 2 | Нет публичных URL объектов | §1.4 п.2 | в коде нет вызовов постоянных URL; в UI нет ссылки вида `https://<bucket>.<s3>/<key>` |
| 3 | Шифрование в покое там, где провайдер поддерживает | §1.2 | настройка SSE на бакете проверена; при отсутствии — запись в журнале решений |
| 4 | Ключ непрозрачный и org-scoped | §1.3 | ключ содержит `organizationId`, не содержит имя файла; попытка передать ключ от клиента отклоняется |
| 5 | Авторизация перед каждым скачиванием | §1.5 | тест: запрос документа чужой организации возвращает отказ **и** не создаёт подпись |
| 6 | Ссылки короткоживущие | §1.5 | `expiresIn` задан явно; тест: ссылка не работает после истечения |
| 7 | Порядок записи: объект → строка | §1.7 | «объект без строки» убирается сборкой мусора; «строка без объекта» — алерт |
| 8 | Согласованность БД и S3 | §1.7, риск R5 | периодическая сверка ключей и строк |

### 1.7 Что происходит с текстами при переносе

1. Экспорт из IndexedDB читает хранилище `documents` по закупкам.
2. Для каждой записи документа: `putObject` исходного содержимого (если доступно) и `putObject` текста;
   в PostgreSQL пишется строка `Document` с ключами, именем, хешем, числом страниц.
3. Ключи детерминированы от `legacyId`, поэтому повторный импорт перезаписывает те же объекты, а не
   плодит дубли.
4. Порядок: **сначала объект в S3, потом строка в БД** в одной идемпотентной операции. Объект без строки
   — безопасно (уберётся сборкой мусора), строка без объекта — недопустимо, поэтому она идёт второй.

## 2. Фоновые задачи: pg-boss

### 2.1 Почему pg-boss, а не Redis

Очередь живёт в той же PostgreSQL, что и данные. Это убирает из требований отдельный сервис, который
нужно разворачивать, мониторить и защищать в РФ, а также убирает риск рассинхронизации двух хранилищ.
Redis добавляется только при появлении конкретной потребности (потребность зафиксирована в
[decisions-and-risks.md](decisions-and-risks.md), решение D5).

| Свойство | Как используется |
|---|---|
| Идемпотентность | каждая задача имеет ключ дедупликации; повторный запуск не создаёт дубль |
| Повторяемость | задачи с `retryLimit` и `retryDelay`, ошибки пишутся в лог |
| Отсутствие потерь | очередь в PostgreSQL переживает перезапуск воркера |
| Расписание | отложенные задачи для отложенных операций |
| Отмена | отмена задач при отзыве операции |

### 2.2 Что уходит в фон, а что остаётся синхронным

Принцип: **HTTP-обработчик не должен ждать тяжёлую работу, но и не должен терять результат.**

| Операция | Решение | Почему |
|---|---|---|
| Разбор большого файла, OCR страниц | фон | минуты, нужен прогресс и устойчивость к обрыву |
| Сборка DOCX / ODT / PDF / ZIP | **остаётся синхронной** | пользователь ждёт файл; маршруты уже работают и покрыты тестами |
| Перенос данных из IndexedDB (импорт) | фон | долгая операция, обязана быть возобновляемой |
| Пересчёт/обновление указателей поиска | фон | производная работа |
| Прокси к ИИ (`/api/chat`, `/api/check`, `/api/requirements`) | **остаётся синхронным** | текущие потоковые ответы и дедупликация в памяти работают; перенос в фон ломает UX |
| Планировщики: напоминания о сроках, проверка истечения сроков фактов | фон по расписанию | сегодня делается в браузере |

### 2.3 Ограничения, которые снимаются переносом воркера

| Ограничение | Где сейчас | Что меняется |
|---|---|---|
| Лимит запросов к ИИ по IP | `Map` в процессе (`rate-limit.ts:40`) | счётчики в PostgreSQL; корректно при нескольких репликах |
| Бюджет ИИ на приложение | `Map` в процессе (`ai-meter.ts:17`) | `AiBudget` в PostgreSQL с атомарным списанием |
| Дедупликация одинаковых запросов к ИИ | `Map` промисов (`ai-meter.ts:41`) | распределённая блокировка на ключе запроса |
| Учёт страниц OCR | счётчик процесса | счётчик в PostgreSQL |

Это **блокеры масштабирования**, а не улучшения: см. риск R1.

## 3. ЮKassa — будущая интеграция

Интеграция выполняется **после** стабилизации серверного ядра, на этапе S10. Здесь фиксируется контракт, чтобы
заранее не построить архитектуру, в которую платежи не поместятся.

### 3.1 Границы

| Правило | Следствие |
|---|---|
| Данные карт не хранятся и не проходят через наш сервер | платёжные данные обрабатывает ЮKassa; у нас только идентификатор платежа и статус |
| Секреты ЮKassa только серверные | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` в переменных окружения, никогда в бандл |
| Вебхук — недоверенный вход | подпись проверяется по процедуре провайдера; тело не используется до проверки |
| Идемпотентность | `Payment.providerPaymentId` уникален; повторная доставка вебхука не выдаёт второй доступ |
| Идемпотентность выдачи | выдача помечает `processedAt` в той же транзакции, что и смену статуса |
| Отмена | `Payment.status = canceled`, возврат средств — отдельной задачей |

### 3.2 Контракт `PaymentAdapter`

| Операция | Контракт |
|---|---|
| `createPayment({ organizationId, amountMinor, currency, description, returnUrl })` | возвращает `{ providerPaymentId, confirmationUrl, status }` |
| `getStatus(providerPaymentId)` | актуальный статус у провайдера |
| `verifyWebhook(rawBody, headers)` | `true`/`false`; при `false` вебхук отбрасывается целиком |
| `refund(providerPaymentId, amountMinor)` | явный возврат, только по решению `owner` |

Доменный код не знает про ЮKassa: он знает про `PaymentAdapter`. Смена провайдера не должна затрагивать
слои 1–3.

### 3.3 Очерёдность

1. Сначала стабилизируются `Organization`, `Membership`, биллинг-состояние и аудит.
2. Затем появляется таблица `Payment` и вебхук-обработчик как единственная точка записи платёжных событий.
3. Только после этого — тарифы и интерфейс оплаты.

Платёжный код не смешивается с этапом переноса данных из IndexedDB: перенос не должен зависеть от
работоспособности биллинга.
