# Core v1 — Phase 0: flow engine + первый модуль

Статус: Phase 0 и R1–R16 реализованы (медизделия 44-ФЗ, общий пакет участника,
matcher характеристик, структурированные реестры, ветка лекарств, ценовые
проверки, запись РУ, сверка РУ медизделия, оптовая надбавка, суммы/форма/срок
обеспечений, расширенная маржа, метаданные ревью, подсказки needs_input,
срок поставки и чек-лист документов); ждёт юридического ревью.
Обновлено: 2026-10-26.
Первый модуль: «Фармацевтика и медизделия».
Зависит от: `docs/core/STATE.md`, `docs/core/figma-board.txt`.

## 1. Цель

Сделать чистое, тестируемое ядро, которое исполняет граф тендерной сферы:
разбор закупки → проверка допуска → расчёт цены → скоринг рисков → решение.
Первый модуль — одна сфера. Остальные 24 добавляются позже как данные, без
изменения движка.

## 2. Первый модуль

Выбран: **Фармацевтика и медизделия**.
Причина: в ChatGPT-чате уже есть подробный чек-лист документов, правовые поля
и риски; на доске есть ветки «Лекарства / Медизделия», нацрежим, РУ, лицензии,
цена и антидемпинг.

Модуль реализован как seed: 4 этапа, 43 правила (26 медицинских + 7 общих +
10 лекарственных), ветки «участвовать / не участвовать / отчёт / подготовка заявки».
R1 ограничен медизделиями 44-ФЗ: evidence-подтверждения, scope-guard, комплект
документов, срок подачи и последствие антидемпинга. R2 добавил общий пакет
участника, R5 — ветку лекарств, R6 — ценовые проверки, R7 — запись РУ лекарства,
R8 — сверку РУ медизделия с реестром, R9 — оптовую надбавку, R10 — суммы
обеспечений, R11 — расширенную маржу, R12 — форму/срок обеспечений,
R13 — метаданные ревью, R14 — подсказки needs_input, R15 — срок поставки.
Правила требуют юридической проверки.

## 5. Контракт (эскиз)

```ts
type FlowNode =
  | { type: "extract"; id: string; fields: string[]; source: SourcePolicy }
  | { type: "question"; id: string; question: string; answer: AnswerKind }
  | { type: "check"; id: string; rule: RuleRef; onFail: Branch }
  | { type: "calc"; id: string; formula: string }
  | { type: "score"; id: string; weights: ScoreWeights }
  | { type: "decision"; id: string; outcome: Outcome }
  | { type: "generate"; id: string; template: string }
  | { type: "report"; id: string; reason: string };

type FlowEdge = {
  from: string;
  to: string;
  on: "yes" | "no" | "value" | "always";
  value?: string;
};

type RuleRef = {
  law: string;
  article: string;
  condition: string;
  requiredDocument?: string;
  validationLogic: string;
  riskLevel: "blocker" | "high" | "medium" | "low";
  effectiveFrom: string;
  source: string;
};

type FlowResult = {
  outcome: Outcome;
  trace: TraceStep[];
  findings: Finding[];
  missing: MissingInput[];
};
```

Фактический контракт — в `web/src/lib/core/flow/types.ts`. В реализации:
- `check` ссылается на `ruleId`, а правило содержит `evaluate`;
- `calc` и `score` содержат `compute`, а не строковые формулы;
- трассировка живёт в `engine.ts`, отдельный `trace.ts` не понадобился.

Главное:
- у проверки есть правовой источник и срок действия;
- отсутствующие данные дают `unknown`/вопрос, а не выдуманное значение;
- результат воспроизводим.

## 6. Критерии приёмки

- Движок исполняет граф с ветками «да/нет» и возвращает детерминированный результат.
- Одинаковый вход + одинаковая версия модуля → одинаковый выход.
- Каждый `check` содержит `law`, `article`, `effective_from`, `source`, `risk_level`.
- Отсутствующие данные не подменяются: появляется `missing` или вопрос.
- Трассировка показывает путь, входы, выходы и источники.
- Валидация модуля ловит: битые рёбра, недостижимые узлы, цикл, дубли ID,
  проверку без источника.
- Первый модуль покрывает 4 этапа и хотя бы один сценарий «не участвовать»
  и один сценарий «подготовка заявки».
- Существующие тесты не изменены и остаются зелёными.
- `npm test`, `npm run lint`, `npx tsc --noEmit` проходят.

## 7. Тестовые фикстуры

Обязательно:
- пустой вход;
- минимальный вход (только обязательные поля);
- пропущенные необязательные поля;
- ветка «да» и ветка «нет»;
- конфликт двух правил;
- правило с истёкшим/будущим `effective_from`;
- дубликат узла/ребра;
- недостижимый узел;
- цикл;
- модуль без правил (должен падать валидацией, а не молча работать).
