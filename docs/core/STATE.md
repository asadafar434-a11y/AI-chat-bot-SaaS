## 1. Цель

Собрать универсальное ядро тендерного SaaS: «документы → требования → сопоставление
с товаром → проверки/риски → чек-лист и заявка», с отраслевыми модулями поверх ядра.

Ядро должно:
- работать поверх существующего продукта, не переписывая его;
- быть пригодным для выноса в отдельный пакет или HTTP-сервис;
- сохранять источник каждого требования, проверки и риска;
- не отправлять персональные данные во внешний ИИ по умолчанию;
- быть детерминированным там, где решение принимает код, а не модель.

Не цель Phase 0: менять UI, схему БД, существующие `/api/*`, IndexedDB или
бизнес-логику `web/src/lib`.

## 4. Архитектура Core v1

```
UI / внешняя платформа
        ↓
web/src/server/core  — адаптеры Prisma/S3/AI/EIS, HTTP API, auth, audit
        ↓
web/src/lib/core     — чистый TypeScript: контракты, flow engine, модули сфер
        ↓
ports/adapters       — RepositoryPort, StoragePort, AiPort, ClockPort, IdPort
```

Позже чистый слой выносится в `packages/tender-core` (npm-пакет) и/или Docker-сервис.
Внешняя интеграция: npm-пакет для TypeScript/Node или HTTP API для любого стека.

### Flow engine

Сферы описываются данными, а не кодом под каждую сферу. Предлагаемые типы узлов:
- `extract` — извлечь поля из документов, сохранить источник и цитату;
- `question` — вопрос с ветками «да/нет/значение»;
- `check` — детерминированная проверка правила;
- `calc` — расчёт формулы;
- `score` — скоринг риска;
- `decision` — «участвовать / не участвовать»;
- `generate` — подготовка заявки/документов;
- `report` — отчёт «почему не участвовать».

Трассировка обязательна: путь по графу, входы, выходы, источники, `unknown` для
недостающих данных. Одинаковый вход → одинаковый выход.

## 5. Решения (ADR-lite)

- D1. Универсальное ядро + отраслевые модули. Не делаем отдельный продукт под каждую сферу.
- D2. Сфера — это данные (граф/правила), а не отдельный код. Ядро не меняется при добавлении сферы.
- D3. Никакого переписывания существующего продукта. Только аддитивные файлы, флаги, тесты.
- D4. Чистое ядро без импортов Next.js/Prisma. Инфраструктура — через порты/адаптеры.
- D5. Правовые проверки версионируются: `law`, `article`, `condition`, `required_document`,
  `validation_logic`, `risk_level`, `effective_from`, `source`.
- D6. ИИ извлекает и предлагает; код проверяет цитаты, числа и правила; человек подтверждает спорное.
- D7. Сначала один модуль и golden-тесты, потом остальные сферы.
- D8. Figma читается через REST API по PAT; токен вне репозитория.
- D9. Phase 0 не трогает БД, API, UI и IndexedDB.

## 9. Ограничения и риски

- Не хранить в репозитории токены, `.env` и персональные данные.
- Не передавать production-ПД во внешний ИИ без отдельного решения и маскирования.
- Не менять существующие `/api/*`, IndexedDB и доменную логику без явного разрешения.
- Не делать destructive-миграции. Только аддитивные изменения и rollback.
- `CLAUDE.md` в корне сейчас описывает support-chat SaaS и расходится с `AGENTS.md`.
  Перед работой в Claude Code это нужно свести, иначе агент получит неверный контекст.
- Figma-токен и DOCX с токеном не коммитить; локальный файл удалить после работы.
